查询工作流

一句话提问进来，经过 27 个节点，一个答案出去。 这一页把图拆开：哪些节点是主干、哪些是分支、失败时系统怎么决定「再试一次」 还是「退回上一轮」。节点的实测行号都在，可以逐个点去核对。

图的形状

图的装配入口是 build_graphs，默认走 reflection 这张图 （另外两张是 fixed——直通不反思，与 empty——调试用空转）。 生产调用只传检查点，其余开关取默认值。

graphs.py:1197 build_graphs graphs.py:1720 _build_reflection graphs.py:305 build_gen_sql_subgraph

主干大致是这条线： 

START → route_intent → parse_date → schema_linking
      → [语义门禁] → fast_match → query_sketch → gen_sql 三节点 → semantics → hitl
      → execute_sql → select → validate → reflect
      → [分析错误 → 回滚重试] 或 → insights → chart → conclusion → output

注意 gen_sql 在顶层不是三个节点，而是一个子图—— 它内部有自己的 generate / validate。子图有独立的装配函数， 所以「agentic 循环」与「经典生成-校验重试」两种形态可以共用同一批上游节点。

意图分流：一条主路，两条岔路

路由节点把问题分成七类（问数 / 元数据 / 写操作 / 闲聊 / 纠错 / 确认 / 归因）， 但图上只有三条走向：

意图去哪为什么
问数 / 归因 主干（parse_date → schema_linking → …） 归因也是问数，只是问题复杂些
元数据 answer_metadata → metadata_check 自校验环 「有哪些表」不该走 SQL 生成，且有独立的自我校验
闲聊 / 纠错 / 确认 / 写操作 各自终态答案节点 这些有确定答案，不需要生成 SQL

graphs.py:1295 make_route_intent graphs.py:1549 _route_after_intent graphs.py:1565 _route_after_refuse

写操作是被显式拦下并拒绝的，而不是「生成一个写 SQL 然后被数据库拒绝」。 拒写在意图层就发生——这是一道保险，真正的安全边界在别处（见安全边界）。

语义门禁：三条出口

schema_linking 之后有一个条件分支，它有三种可能的结果。 这段逻辑看起来只是路由，其实是「语义优先」这个产品定位的落点：

graphs.py:1679 _route_semantic_gate_after_linking graphs.py:1690 _route_semantic_gate_after_linking_fast_match graphs.py:1698 _route_semantic_gate_after_linking_gen_sql

三种结果分别对应：硬 MISS → refuse（拒绝并引导扩展模型）、 正常 → 继续（快径或生成）、数据源没有语义模型 → refuse。 软 MISS 不走这条分支——它跟着计划一起流下去，产出骨架。

细节在语义层与产品概念。

结果校验：规则链，不是模型判断

执行完之后，结果要过一条确定性规则链。规则按注册顺序执行， 第一条失败的规则胜出——顺序就是优先级，最具体、最便宜的在前面。

rules.py:212 Rule rules.py:232 verify

族检查什么
F1 形状「最高是多少」这类单值问题必须只返回一行一列
F4 排序问题里说了「最高/最低/前几」，SQL 里得有对应的排序
F2 过滤问题里点名的实体，必须在 SQL 条件里出现
F3 取值类型、唯一性、取值范围是否合理

这些都是纯代码、零 LLM 的判断。它们的价值不只是「省一次模型调用」，而是 可回归测试、且换模型不退化——一条规则写对了，它永远对。

回滚阶梯：失败之后怎么走

失败会进入 analyze_error，由它决定回滚到哪一步。 这里最容易犯的错是「无脑重试」——那会让系统在两轮之间来回振荡，烧钱且不收敛。 所以每一轮的 SQL 与结果签名都被记下来，跟上一轮做确定性比对。

versions.py:60 record_version versions.py:32 result_sig versions.py:89 regression_state

判定含义含义背后的动作
无效修复 改了 SQL 但结果签名没变 这一轮白改，反馈里要明说「你刚才那个改动没生效」
没有进步 结果变了，但规则链仍然失败在同一处 问题不在被改的地方，别再沿着这条线试
问题漂移 原来失败的点过去了，却冒出一个新的失败点 可能是修一个坏一个，需要警惕

versions.py:126 regression_report graphs.py:1261 _route_after_reflect

为什么「反馈」比「重试次数」重要

同一个模型、同样的提示，重试一次大概率得到同样的错误。真正让它改变方向的是告诉它上一次错在哪——而这恰恰是不该让模型自己判断的部分：模型倾向于认为自己上次是对的。

所以这里的反馈是算出来的，不是感觉出来的。

重试有硬上限。MAX_REFLECT_RETRIES 是执行错误、规则失败、一致性、 裁决共享的一个总闸——到顶就交付当前最好的结果，并把不确定性说清楚， 而不是无限循环。

预算由若干信息块竞争，块有优先级（少样本示例与用户事实最高，画像最低）。 装块之后还有一层块内裁剪——优先级决定「哪个块先被看到」， 相关度决定「块里哪几条先被看到」。设计意图见 Agent 能力 · 上下文工程。
