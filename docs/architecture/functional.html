功能架构

这一页讲 Trove 的功能与边界：产品有哪些功能块、分给谁用、 怎么串成一条链路、哪些事刻意不做。代码怎么分层在系统架构， 一次提问经过了哪些节点在查询工作流—— 本页不重复机制细节，只把功能说全、把边界划清。

两个界面，三种角色

Trove 对外只有两个界面：用户端（提问与读答案）与 管理台（治理与运营）。功能按角色投放—— 用户看到的数据源也已被两层授权筛过（数据源授权 + 主题域授权）， 只有「已连接且知识库已初始化」的数据源才可能出现。

能力的投放方式：挂载，而不是拦截

管理台入口、生成时的 schema 枚举工具，都是按角色与档位挂载的：不具备就不出现，而不是出现了再被拦回来。服务端接口另有自己的鉴权（fail-closed）——两道门各自成立。

角色在哪工作能做什么
普通用户 用户端 提问；读答案的每一块（结论 / 结果表 / 图表 / 依据抽屉 / 归因分析卡）；会话管理与反馈；切换主题域
分析员 用户端 + 管理台（只读） 普通用户的全部；管理台只读浏览（数据源、知识库、语义层、判定历史等）；生成时可用 schema 枚举工具（值确认 / 结构懒加载 / 执行计划）。不能改任何治理内容
管理员 管理台 数据源注册、知识库初始化 / 学习与确认、语义模型编辑与版本回滚、判定规则、订阅与定时任务、行动审批、Skills、记忆确认、主题域与授权、审计、系统设置与模型配置

功能块：四段链路，一层支撑

首页把 Trove 概括为一条链路——问数 · 分析 · 决策 · 行动。 落到功能上，每一段都有用户端形态与管理端配套。图 1 是功能分解（不是调用图）： 四段链路在上，一层横向支撑在下——支撑层不对应某一个环节， 而是所有环节共用的治理与沉淀。

横向支撑层

支撑层是功能「用起来之后变准」的地方——它不直接回答问题， 但决定了下次回答的依据从哪来、谁说了算。

功能块谁在用一句话
知识库 管理员（+ 自动草案） 五个 YAML 按「谁能写」分工；自动写入一律 pending，管理员确认后才进检索
语义模型 管理员 可答边界的唯一声明处：初始化起草、可视化编辑、版本历史与回滚
记忆 自动 + 管理员确认 情节记忆（问过什么）自动可用；偏好与晋升先落草案，确认才生效（晋升默认关）
Skills 管理员 组织方法论（区别于数据源事实）：三档——整段注入、按需加载、只断言不注入
主题域 · 权限 · 审计 管理员 给问题划范围 + 第二层授权收窄（不可见即不存在）；角色授权、审计日志、API 令牌
质量与成本运营台 管理员 评测对比与回归门：答得对不对、花得值不值摊开成一页

产物链：谁产生，谁消费

把上图拆散看，功能之间真正流动的是产物—— 这也决定了「用起来会变准」具体是怎么发生的：每一次问答与判定都在留下 下一次要用的东西，而自动留下的部分必须过确认门。

产物谁产生谁消费落在哪
答案卡（结论 / SQL / 证据） 问数管线 提问者；依据抽屉随时复查 会话记录
归因卡 独立的只读分析 提问者 会话记录（不成时不出现）
情节记忆 每次问答自动写回（事实记录） 下一次生成：成功 SQL 当锚点、失败与纠正当反例 本机记忆库
待确认草案（示例 / 教训 / 偏好） 自动沉淀 管理员确认 知识库的 pending 区 → 确认后进检索
判定（verdict + 证据） 定时判定引擎 判定历史、订阅推送、行动提案 判定运行记录
行动提案 判定触发 管理员审批 提案台
交付与回执 审批通过后的拉通道 外部系统；回执回来对账 审计轨迹

这条链上有一条贯穿的分工：凡是「算不算、对不对、变没变好」的判断 都交给确定性代码——门禁判定、编译器、结果规则链、版本比对、 判定引擎、审批留痕，全是零 LLM；LLM 只负责理解与表达。所以「行动」才可能 停在一份可审计的提案上，而不是一个不可解释的自主执行。

边界：刻意不做的事

下面这些不是待办清单，是产品口径的一部分—— 写出来，才不会在演示时被过度承诺。

不做的事为什么
不由 Trove 执行行动 系统只到「提案 → 审批 → 交付 → 回执」；执行与后果在外部系统——行动在系统外是刻意边界，不是缺口
自动内容不直接进检索 记忆 / Skills / 教训的自动写入一律落 pending，晋升默认关——人工确认是知识库不被污染的闸门
未建模的数据源不开放问数 语义模型是可答边界的唯一声明处：接入即建模——先初始化知识库，再开放给用户
判定不做「AI 判断」 阈值规则声明式（无 eval 的闭集表达式）、三值逻辑、证据可回放；「判不了」绝不报成告警
人工环节默认拒绝 人工确认与行动审批的失败方向都是不放行——拿不准时宁可停在原地
