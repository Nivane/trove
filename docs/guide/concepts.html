产品概念

这一页解释 Trove 与「Text2SQL」的差别在哪：它不把问题直接翻译成 SQL， 而是先判断这个问题能不能答、按谁的口径答，然后才生成。 理解这套概念之后，后面所有页面的设计取舍都会变得理所当然。

语义模型：可答边界的来源

每个数据源有一份 semantics.yml，它不是「提示词素材」，而是这个数据源的 契约：哪些指标存在、每个指标怎么算、哪些字段是维度、表之间怎么关联。 文件格式遵循 Apache OSSIE 的 core spec——顶层是 semantic_model， 下面挂 datasets 与 metrics，指标表达式按方言分别给出：

ossie_format.py:40 dialects ossie_format.py:76 semantic_model

这里有一个容易忽略但很关键的机制：一个指标属于哪些数据集，是算出来的，不是声明的。 解析器拿指标表达式去过一遍 SQL 语法树，凡是被表名限定的列，其表名若在已声明的数据集里， 就记一笔归属：

ossie.py:68 _dataset_refs ossie.py:108 parse_ossie

为什么值得这么做：如果归属靠人手写，它就会和表达式本身分叉——改了公式忘了改归属， 系统就会在一个错误的表集上算这个指标。从表达式反推则不可能分叉，而且反推不出来 （表达式里全是裸列、没有任何表限定）时它会报错而不是猜。 这也解释了为什么指标表达式必须写成表限定形式：loans.amount，不是 amount。

单一真源

语义模型的真源是 KB 里的 semantics.yml（由 /kb init 起草、人审确认）。配置目录下的语义文件只作补充，不覆盖它——两个真源等于没有真源。

可答边界：不是「全有全无」

有了语义模型，就能在生成之前判断一个问题的命运。编译器的判定结果有三种，而不是两种：

结果含义下游动作
编译成功 计划被完整翻译成 SQL，可解析部分全部权威化 直接执行，生成通道基本不参与
软 MISS 词表/取值/口径未声明，但结构是清楚的 产出骨架，交给生成通道补齐，回答照常交付
硬 MISS 结构性问题：会产出错误的行集 拒绝并反问，引导扩展语义模型

compiler.py:1036 SemanticCompiler compiler.py:1380 compile_detailed compiler.py:622 CompileMiss compiler.py:635 PartialCompile

哪些算硬 MISS

分界线只有一条：放行它，会不会算出一个看起来对、其实错的数。会，就是硬 MISS。 典型的是这四类结构性问题：

reason为什么放行会出错
fan_out 一对多 join 把被聚合的行复制了多份，聚合结果被放大
ambiguous_join_path 两张表之间有多条关联路径，选错一条就是另一个口径
unreachable_table 问题涉及的表不在本次匹配集里，生成会引用未覆盖的表
derived_cycle 派生指标的定义成环/超深/悬空，展开它没有意义

compiler.py:695 HARD_MISS_REASONS compiler.py:714 SOFT_MISS_REASONS compiler.py:657 MISS_REASONS

判定函数有一个刻意的默认值：遇到不认识的 reason 一律按硬处理。 宁可多拒绝一次、让人来确认，也不要把一个没见过的结构性问题当软问题放过去。

compiler.py:736 is_hard_miss

分级逃生梯

拒绝是最后手段，不是第一反应。Trove 的边界是分级的：能救的救，救不了的才拦。

软 MISS：产出骨架，而不是停摆

软 MISS 意味着「结构我们懂了，只是某个词没登记」。这时编译器不会整体放弃， 而是把能权威化的部分（join 路径、过滤条件、分组）编译成骨架固化下来， 未解析的组件留给生成通道按计划文本补齐。

骨架是「半成品」还是「约束」？

关键在于执行前还有一道骨架保真校验：生成通道补完的那条 SQL，必须仍然保留骨架里的 join 边、WHERE 条件与分组宽度。少一个 join、丢一个过滤，校验不通过，SQL 不放行。

所以软 MISS 不是「降级成裸表生成」，是「权威部分被钉住，剩下的填空不许改动已钉住的部分」。

execute_sql.py:153 skeleton_preserved compiler.py:2500 skeleton_preserved contract.py:160 PlanContract

硬 MISS：拒绝 + 反问 + 扩展模型

硬 MISS 走的是反问扩展这条路——拒绝不是终点，是引导用户把语义模型补全：

  1. 路由短路到 refuse 节点，携带结构化的分因（是 fan-out？还是 join 二义？）。
  2. LLM 依据分因草拟一份最小扩展草案——要补什么字段、什么指标、什么枚举值。
  3. 草案先做冲突检测，再作为 pending 草稿写入 semantic_drafts.yml，不碰 semantics.yml。
  4. 管理端确认后应用到 semantics.yml 并刷新镜像。
  5. 用户的原始问题重新作答——这一次它落在边界之内了。

refuse.py:484 make_refuse semantic_draft.py:229 draft_refusal_extension manage.py:396 SemanticManager

「管理端确认」在主路径之外还有一条自动档：如果草案补的字段能在物理 catalog 里直接找到、 或者补的指标能通过机械的聚合验证，系统会直接落库，不再等人点确认。这条路的边界写死在代码里， 认不出的仍然回到人工那一档。

refuse.py:576 A 档 = 物理列字段

两条快径，别混为一谈

系统里有两种「不调用模型直接出 SQL」的机制。它们经常被当成同一件事，但触发条件、 依据、风险模型完全不同：

模板快径KB 精确命中
依据 examples.yml 里 kind='template' 的条目 examples.yml 里语义等价的问答对
触发 问题与模板四重硬约束全部满足 词重叠 ≥ 0.95
产出 把参数填进模板 SQL 直接复用示例 SQL
兜底 任一约束不满足即放弃 修正轮禁用（避免复读错误答案）

模板快径的四重约束是：SQL 形状合格（单表、无 JOIN/子查询/CTE、无 GROUP/ORDER/LIMIT、单聚合）、 问题含聚合意图词、表锚定一致、有家族证据。它是零 LLM 零网络的纯函数， 所以能在毫秒级给出答案，而且答案天然可解释——命中了哪条模板，是查得出来的。

fast_match.py:367 make_fast_match fast_match.py:136 template_sql_shape_ok graphs.py:153 KB_EXACT_OVERLAP

模板快径只用 kind='template' 的条目——这是 KB 防作弊约束的直接体现： 模板是 /kb init 的确定性产物，人往里塞的东西不会成为快径依据。

知识库：五个文件，三种角色

KB 不是一堆配置，是按「谁写、谁能改」分工的五个文件：

文件内容谁来写
schema_notes.yml 表/列的语义注释 /kb init 起草，人可改
semantics.yml 语义模型（数据集 + 指标） /kb init 起草，人可改
examples.yml 问答对与模板 /kb init + /kb learn，人审
rules.yml 生成时必须遵守的规则文本 纯人工，没有写入器
lessons.yml 教训（失败模式与规避） 蒸馏路径懒创建，两档确认

service.py:3 human-editable init_pipeline.py:308 INIT_FILES

两个值得记住的细节。其一：/kb init 只产出三个文件 （schema_notes.yml、semantics.yml、examples.yml）， lessons.yml 是后续反馈路径首次写入时才创建的——刚初始化完的 KB 里没有它，是正常的。 其二：rules.yml 是唯一没有程序化写入器的文件，它只能由人编写， 这意味着它承载的是组织口径而不是系统推断。

人工确认门禁：pending 不进检索

凡是系统自动生成的内容——好评问答、修正记录、蒸馏教训、自动回写的样例—— 统一以 pending 落盘。读侧有明确的过滤器：pending 的示例与未确认的教训， 根本不参与检索，等于不存在。

service.py:570 pending 草稿不参与检索 service.py:1609 confirmed service.py:1817 pending

这道门禁是刻意不可绕过的

「自动回写 → 自动注入」是个很诱人的闭环，但它会让 KB 被自己的输出污染：一次错误的修正变成教训， 下次生成照着这条教训走，再产出一个错误答案、再蒸馏出一条教训。几轮之后没人说得清 KB 里哪些是真的。

所以确认门禁不是流程负担，是防污染的必要代价。记忆子系统里唯一豁免的是「情节记忆」—— 它记录的是「当时发生了什么」这类客观事实，不是可复用的知识。
