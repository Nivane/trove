Trove 能力地图

把一句自然语言提问，变成可解释的 SQL、图表与结论。 Trove 把确定性押在语义模型、节点化工作流与确定性安全层上， 只把真正需要模型的那一段交给 LLM——所以跨厂商、跨方言下行为可预期。

English summary Trove is a conversational data agent that turns a natural-language question into explainable SQL, a chart and a written conclusion. It is semantic-first: an OSSIE semantic model defines what is answerable, a deterministic compiler resolves joins, enums, time buckets and derived metrics, and a 28-node LangGraph workflow generates, validates, executes and reflects — with an agentic ReAct loop driving SQL generation. This page lists what it does; every capability links to the file that implements it.

全貌 · 01

它是什么

一个可自托管的问数分析 Agent：接入你自己的库，用自然语言提问，拿到 SQL、图表和一段有依据的结论。 提问与修正会沉淀进该数据源的知识库，准确率随使用增长。

# 一次性提问，输出 JSON
echo "哪个地区的平均贷款金额最高?" | uv run trove-cli --datasource demo --print

# 前后端分离部署，浏览器访问 http://localhost:8080
docker compose up --build
全貌 · 02

为什么语义优先

大多数问数系统的准确率上限押在模型和检索上。Trove 换了一个问题： 这个数据源到底能回答什么——把这件事用一份可读的语义模型写清楚， 先划定边界，再谈生成。

语义模型是生成的主视角，也是可答边界。但它不是一道全有全无的闸门—— 编译结果是分级的，能答多少答多少，答不了的说清楚为什么：

命中 HIT
编译器直接产出 SQL。join 路径解析、枚举词归一、时间分桶、派生指标与比率指标递归内联， 全部在确定性代码里完成，不走模型。
软 MISS
产出骨架，按计划补齐。词表、枚举值、未声明口径这类缺口会留下 PartialCompile：能解析的部分（join、过滤、分组）先权威化， 剩余组件交给生成节点按计划文本补齐，回答照常交付。
硬 MISS
拒绝，并反问怎么把模型扩起来。结构性缺口——fan-out、join 二义、未覆盖的表、坏掉的派生定义—— 拒绝硬猜，改为向用户澄清口径，并把这次澄清沉淀成语义模型的扩展建议。

02

判定规则——同一份语义模型，回答「算不算有问题」

规则用语义模型的词表说话：一个 metric、一组 filter、一个自然语言窗口、一个基线， 外加「什么算超标」的布尔表达式。定时任务按规则求值，全程零 LLM—— 于是「昨天为什么报红」可以从输入重放出来，而不是重跑一次对话看它今天心情如何。

条件是不可信输入（任何能写 KB 的人都能改），所以绝不过 eval()： 手写分词器 + 递归下降，变量表与函数表都是闭集，拼错的变量名在解析期就报错。 求值是三值的——通过 / 违反 / 判不了：只有两值时，「缺基期」会让 not (x > y) 为真，一条「没数据就报警」的规则反而会在数据缺失那刻触发。

边界

怎么验证，而不是信谁的数字

这个页面不给准确率数字。问数系统的准确率高度依赖数据集、方言、语义模型完备度， 不同口径的数字放在一起没有意义——而且换个数据源就作废。所以这里给的是复现路径。

仓库自带一条完整链路，你可以用自己的题、接自己的库跑一遍：

# 1. 内置 BIRD 金融演示数据源，零配置先看效果
uv run trove --datasource demo

# 2. 接上你自己的库（MySQL / Doris / PostgreSQL / ClickHouse / DuckDB）
uv run python scripts/lint_kb.py --db-id <你的库> \
    --datasource mysql://user:pass@host:3306/dbname

# 3. 换成你的题目集跑评测，代价敏感，按需手动跑
uv run python scripts/eval_bird.py --kb-dir <你的 KB 目录>

# 4. 拿到 baseline 后，之后每次改动都过一遍零成本回归门
uv run python scripts/eval_gate.py --baseline <旧结果> --current <新结果>

第 4 步是这套评测设计的关键：判定落盘之后，回归检查不调用任何模型、不碰网络， 所以它可以进 CI，也可以在你提交前顺手跑一次。

向前

路标

正在推进的八个方向。这里写的是方向与判据——一个方向做到什么程度算做到了， 而不是承诺日期。

每条判据下面另有一行装置：靠什么保证它，以及那个装置今天缺哪一块。 没有装置句的判据只能靠人工复核，就没法用来排期——所以八条目前都还没有走完， 每条的缺口都写在下面，不藏在「进行中」里。

01

语义漂移治理

业务口径会变，语义模型会旧。让「模型与真实数据已经对不上」这件事被自动发现、可定位到具体条目。

判据漂移报告能精确到数据集/字段/指标条目，且不依赖人工巡检。

装置分类学列了 L1–L4（结构 / 引用 / 语义 / 口径），门禁脚本 scripts/check_drift.py 实际渲染 L1–L2（零 LLM，退出码 0/1/2，区分「没漂移」与「没查成」——只跑了 L1 的 ok 报告不许写成 OK）。后台周期检测落进同一个漂移库，与 /v1/admin/drift 读写同一份文件。出口已通：门禁脚本已进 CI（backend.yml 的 lint 作业，守的是仓库里那份 demo KB）——「不依赖人工巡检」不再只靠人记得跑。仍缺：L3/L4 未落地，判据里「指标」这一格今天还进不了报告（L3 要探查活库取值，探测未接；L4 按设计只承接外部声明、不自行检测）。

已补后台周期检测的出口。此前结果只进 logger.info——在跑，但白跑：没有可查询的行、没有退出码、没有告警，跑一周也答不了「哪个库漂过」。现走 drift 模块既有的写入路径（drift_run + 条目两张表），归一化用那份认得 status/skip_reason 的适配器，所以「没查成」不会被洗成「无漂移」。落库的是全部数据源、返回的只是有漂移的那些：落库要「查过了」的完整证据（含干净的一次，否则历史里只剩有漂移的那几次，读起来像这个库一直在漂）；返回给调用方的是「要不要吭声」。

02

执行画像

把每次执行的代价与形态沉淀成画像：哪些查询在变慢、哪类问法代价最高，让优化有据可依。

判据画像数据来自真实执行观测，且采集本身不给查询增加可感知开销。

装置执行证据的三态形状已落地（没查过 / 查过但不知道 / 有值），并有测试禁止拿返回行数冒充扫描量。缺观测面：扫描量这一格六个方言都还没读，scanned_rows 恒空——「来自真实执行观测」今天只对行数成立。

03

已验证查询资产

被人确认过的正确答案应当可复用、可溯源，成为知识库里的一等资产，而不是一次性消耗品。

判据复用不改变现有匹配判据的去向，且每条资产可追溯到它的确认人。

装置治理维度（status / owner / approved_by / approved_at / source）随确认逐条写入 examples.yml，certified 必须有人，认证门不过整批拒绝——「每条资产可追溯到它的确认人」已成立。缺的是台账：AssetLedger（runs / p50_ms）已实现、有测试钉住，但没有任何生产构造点；且 status 还没参与检索加权。

04

可核验闭环

结论不仅要给 SQL，还要能说明它凭什么成立——把校验过程也变成可复核的产物。

判据任意一条交付结论，都能沿着证据链走回原始数据。

装置证据链的下半段已落地（执行证据：估算 / 实际 / 三态新鲜度）。缺上半段：从结论出发回走到执行这一段还没有——「任意一条」今天不成立。

05

语义分支评审

同一份语义模型的多条演进路线，应当可以并行比对后再合入，而不是只能线性覆盖。

判据分支评审的结论对最终合入有约束力，而非仅供参考。

装置还没有。「有约束力的评审」所需的形状（GateDecision / SemanticChange）已定义在漂移治理模块里，但没有任何实现与调用点——判据今天不可达，这条是八条里离得最远的一格。

06

身份鉴权与字段脱敏

把可答边界从「这个数据源能答什么」推进到「这个人能看什么」——先落执行前的表级授权门与字段级脱敏，再谈编译期收窄。

判据判定落在执行前而不是结果后置过滤：未授权的表不发出查询，越权字段不进入模型上下文（脱敏在 LLM 之前），每一次拒绝、改写与凭 scope 读原文都留下审计。

装置执行前的 Authorizer（A1 主体 → A2 数据源 → A3 表级三道） + LLM 前的 Masker + 审计日志与指标，都已在执行路径上。剩一处缺口：表级门默认 warn（命中只放行、不拦）——切档要等观察期的误伤数据，那要真部署才收得到。

已修解析把 CTE 名当成物理表（FROM <cte> 与 exp.Table 同形）。后果是与权限无关的误拒：只要查询里有 CTE 就可能被拦，基线实测 32 题里 2 题命中。已与 services/sql/guard.py 的判据同源，修后基线 0 命中。

已补warn 命中的遥测出口。此前只有一行日志与 state.authz_decision——「跑一周看哪些表会被拒」收不齐（一行一条的日志答不了聚合问题）。现为三条出口，各答一个问题：日志给现场，trove_authz_table_warn_total{datasource} 给量（切 enforce 会打挂多少），审计行 authz.table_warn 给名字。计数器与拒绝计数分家——混在一起，告警率里会有一半根本没被拦的查询；表名不进标签（基数随库增长而无限），名字落在审计行上。

07

成本归因与预算

让每一次问答的 token 花在哪一步、为什么花，成为可查账、可设限的量。

判据归因覆盖全部模型调用路径，不存在「不产生记录」的调用。

装置LLM 调用点清单的 AST 枚举测试（枚举 .chat / .chat_full / .chat_stream / .embedding）。两个盲区：全部 34 个调用点里仍有不记账的；且清单只枚举「谁在调模型」，看不见 prompt 的字符串构造——调用点没变、投递内容变了，它不红。

08

不可信数据输入边界

数据库里的内容来自外部世界，不该被当成指令。值进入模型上下文只有两条通道——模板渲染与工具回喂；隔离收成一个核钉在这两条上，不靠调用点自觉。

判据新增数据源、新增提示词参数默认被扫，要放行必须显式登记；第三条路不存在——调用点由 LLM 调用点清单枚举保证，往 prompt 上挂内容由单一门保证。

装置隔离核（llm/untrusted.py）+ 19 个名字的白名单（默认扫，放行必须显式登记，理由写进表里）+ 第三档信任级 AdminConfirmed（豁免来自登记，不来自内容长相）+ 守卫与快照测试。org skill 的追加只留一个门：fence_org_skill 围栏兼标注来源，append_skill_block 是唯一追加点。

已修组织级 skill 正文此前是散落的 f-string 追加——既不经过模板渲染、也不经过工具回喂，隔离核的两条通道都够不着它；两档处置还相反：required 档原文进 system prompt（零扫描），available 档经隔离核整值作废，一句话让整份方法论变成 [data: content isolated]。现已两档同策略：围栏 + 来源标注、不净化内容——指令性文本的可信来自人确认过的登记。写入关口另扫一遍投递面（描述 + 正文，两档都扫），命中在响应里报给管理员（injection_hits，报而不拦）。清单的盲区（只看得见「谁在调模型」，看不见字符串怎么拼）已写进那份测试的文档串，由单一门补，不靠扩清单。

定位

这套设计押在哪

把确定性押在可编排的节点化工作流、多库多模型抽象与确定性安全策略层上，而不是押在模型与检索的单点强度上——所以跨厂商、跨方言下行为更可预期。

Design bet: put determinism in an orchestratable node graph, a multi-database / multi-model abstraction, and a deterministic safety layer — rather than in the strength of one model or one retriever.
