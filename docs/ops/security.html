安全边界

问数系统要执行模型生成的 SQL。这一页讲 Trove 怎么把这件事变安全： 只读的三层门、限流、加密、审计，以及几处刻意选择「失败时拒绝」而不是「失败时放行」的地方。

只读执行：三层门

「只允许 SELECT」这句话在三个不同层次上被检查，而不是只在一个地方：

层做法拦什么
① 关键词正则 廉价的首层筛查 明显带 DML/DDL 关键字的语句
② AST 防火墙 SQLGlot 解析成语法树后整树扫描 数据修改型 CTE、SELECT ... INTO OUTFILE 等伪装成 SELECT 的写操作
③ 执行器统一门 最终执行入口再查一次 任何绕过前两层的路径

guard.py:50 check_readonly guard.py:100 find_all registry.py:413 _guard_read_only

为什么必须做到 AST 级

正则挡不住这种：WITH x AS (DELETE FROM t RETURNING *) SELECT * FROM x。 它以 WITH 开头、含 SELECT，看起来人畜无害，实际在删数据。

要发现它只能真的解析成语法树，然后扫描整棵树的 DML/DDL 节点—— 而不是只看第一个词。

真正的边界在数据库侧

代码里对这一点写得很直白：真正的授权边界仍然是数据库侧的只读角色。 三层门是纵深防御，不是「有了它就可以给写权限」的理由。

给 Trove 一个只会 SELECT 的账号，是这里性价比最高的一件事。账号怎么建见 接入数据源。

执行侧的资源上限

限制值作用
试跑取数10 行agentic 循环里的 probe_query
试跑超时5 秒探测不该拖垮循环
规则校验取数50 行规则只消费行数/首行值/列形状，50 足够

gen_sql.py:593 PROBE_LIMIT gen_sql.py:595 PROBE_TIMEOUT_S gen_sql.py:795 CHECK_RESULT_LIMIT executor.py:36 timeout_ms

注意试跑超时（5s）与执行超时（30s）是两个不同的数。 一个模型自发的探测不该占用正式执行的预算，卡住它就该快速失败、换个思路。

自检：怎么确认那道边界真的在

「边界在数据库侧」这句话本身得有人验。启动时 Trove 会问每个数据源一句： 这个账号到底能不能写？结论会 WARN 到日志，并作为每个源的 readonly 字段出现在探活端点上。

它绝不「试写一条语句」

用一条「必然失败的写语句」来验证只读，是最容易想到也最不该做的事： 它「必然失败」的前提，正是「账号只读」这个还没有被证明的假设。 账号其实可写时，那条语句会真的写进去——一个探测变成一次生产写入。

所以自检只查权限表：MySQL/Doris 走 SHOW GRANTS，PostgreSQL 查 pg_roles / pg_class / table_privileges， ClickHouse 查 system.grants（含角色继承展开）。一个字都不写。

datasource/readonly.py 自检编排 core/types.py ReadonlyProbe

限流与配额

业务端点按用户限流，两个维度叠加：每分钟的令牌桶，加上每日总配额。 被限流拒绝的请求不计入日配额——这一点是对的， 否则一次突发会把当天的额度烧光。

维度默认关掉
每分钟请求30设为 0
每日配额300设为 0
登录尝试5 次 / 15 分钟环境变量调整

deps.py:193 check_api_rate config.py:248 api_rate_per_minute ratelimit.py:24 TokenBucket

限流是进程内实现。单实例部署下这是准的；多实例部署时每个实例各限各的， 实际额度会翻倍——这是当前实现的一个已知边界，需要严格限流时应在网关层再做一层。

认证与授权

鉴权是 fail-closed 的：没有认证组件时服务拒绝启动，而不是裸奔运行并打条警告。 这条设计在系统架构里也提到了—— 它是「宁可起不来，也不要静默地不安全」。

app.py:213 auth is None deps.py:73 get_current_user deps.py:137 require_scope

授权有两个层次，容易混淆，值得分清：

概念是什么用处
账号角色 admin 或非 admin 决定能不能进管理端
工具 ACL 角色 analyst（admin 隐含） 决定生成时能看见哪些 catalog 工具
数据源 grants 用户 ↔ 数据源的授权表 决定能问哪些源

analyst 不是一种账号角色——没有「analyst 账号」这种东西。 它是工具可见性的过滤键：授予后，生成节点里那几个能摸物理 schema 的工具才对这个人可见。

policy.py:132 Principal deps.py:156 require_datasource

数据源 grants 的语义是三值的，而且三值都落在安全的一侧： None（拿不到授权依据）拒绝一切；空集合只放行默认数据源； 非空集合是严格白名单。所以「忘了授权」和「读不到授权依据」都不会退化成放行。

判定只有一份实现

这套策略统一在 services/authz/policy.py，HTTP 侧与 MCP 侧都调它。 此前两处各有一份手抄，已经漂移过——同一个策略抄两遍就会有两套行为，这正是收口要解决的问题。

执行前的授权门

上面那套判定此前挂在路由的装饰器上，语义是「这个端点需要授权」。 于是任何不经路由的入口——API 直执行、job 载荷、CLI、MCP——都绕开了它。 现在它被下沉到执行前的最后一米： execute_sql 节点里，无论 SQL 从哪来都要过这一道。

拒绝是终止，不是一次修正轮。让模型重写十遍也改不掉「这个用户没有这张表的权限」， 只会烧掉共享的修正预算，所以拒绝不喂回生成节点。

execute_sql.py:163 执行前的最后一米 enforcer.py Authorizer

表级判定默认只警告不拦（authz.table_enforcement: warn）。 原因很实在：存量 grants 只到数据源级，直接拒绝会让正常查询大面积 403， 把一次安全改进做成事故。先跑一段收集「哪些表会被拒」，再切 enforce。 数据源级判定与「必须有主体」不受这个开关影响，恒为拒绝。

被拒的次数按原因计数（trove_authz_deny_total{reason}）， 不按人：单看总数读不出「是没配主体，还是表没授权」，而这两者的处置方向相反 ——一个是部署没接好，一个是该加 grants。计数记在执行节点而不是判定服务里， 因为同一个判定函数也服务于「只判定不执行」的调用，那些没有落库 （与成本轨「节点记才等于这条查询落库了」同一条纪律）。

放行的那些要分开记。观察期最要紧的数不是「拒了多少」（此时恒为 0）， 而是「本来会拒多少」——所以 warn 期的命中单记一条 trove_authz_table_warn_total{datasource}，与拒绝计数分家： 并进同一个系列，运维读到的告警率里会混进一半根本没被拦的查询。 这条计数器回答量；名字（哪些表会被拒）落在审计行的 authz.table_warn 上——表名不进指标标签，基数随库增长而无限 （同「路由用模板而不是原始 URL」）。

观察期只靠日志是收不齐的：一行一条的日志答不了「一周里哪些表」这个聚合问题。 三条出口各答一个问题——日志给现场，计数器给量，审计行给名字。

字段级脱敏

RLS 管行，此前没人管列——手机号、身份证、邮箱照样出到前端与模型上下文。 现在在语义层声明字段的脱敏模式，SQL 验证之后、任何模型节点之前改写结果值。

模式结果用在
partial138****8888还要能对上人的场景（客服报号）
hashsha256(salt+值) 前 12 位要能分组/去重但不要原文（同一值仍映射到同一串）
null—只当存在性用

masking.py:340 Masker.apply nodes/masking.py 脱敏节点

绕开脱敏看原文靠 scope 而不是 role：持 pii 的账号可以按原文取， 而 admin 不自动获得这个能力——管理员的身份是「能改配置」，不是「能看身份证号」。 每一次绕开都会写一条 masking.bypass 审计。

三条边界值得知道：脱敏按投影位置匹配，所以 SELECT * 与 函数/聚合投影（sum(amount)）拿不到位置，走的是列名兜底或有意不脱敏； 模型与 salt 读不出来时拒绝执行，不降级为明文； 值本身不写日志、不写审计——审计只记「对哪些字段用了哪种模式」。

以用户身份重放

排障时最常问的一句是「用户 A 看到的到底是什么」。此前只能借账号。 现在 admin 可以在自己的会话里带 on_behalf_of 重放： 

POST /v1/chat  { "question": "...", "on_behalf_of": "user:42" }

四道校验在流开始之前跑完：发起人是 admin、会话属于发起人、目标用户存在、 subject 类型只认 user:。缺一道，这就是一条 admin 的越权读取通道。 重放期间发起人的 scopes 全部不参与判定——目标用户的权限才是这个视图该有的全部， 「减掉 pii 一项」是一张永远列不全的清单。

审计双记：authz.on_behalf_of 记「谁发起了一次重放」， query.execute 的 details 里另带一条 on_behalf_of——排障的人先翻的是查询记录， 只在另一张表里记一次意味着要拼两张表才知道当时的身份。

chat.py _replay_subject session.py _replay_wire

前端会在答案上方标出「已脱敏字段 N」；bypass 的那次单独显示为「原文」—— 那次字段表是空的，写出来会读成「本次没脱敏」，而事实恰好相反。 表头命中的列也有标记，名字对不上就不标（宁可少标，不给没被改写的列打上标记）。

凭证与加密

数据源连接串里的密码在落盘前加密（TROVE_SECRET_KEY 作为密钥）。 加密值带 enc:v1: 前缀标记；没有前缀的是旧版明文， 读时透传、下次写时自动加密。

secrets.py:123 TROVE_SECRET_KEY secrets.py:39 enc:v1

这个「带前缀标记 + 向后兼容」的形态让迁移不需要一次性的批处理： 存量明文能继续用，随着配置被重新保存自然加密完成。

模型 API key 建议走环境变量或配置文件里的 ${ENV_VAR} 占位符—— 这样配置文件本身可以进版本库。详见配置参考。

审计

管理操作会写入审计日志，管理端有查询端点。另外，检索层有自己的查询日志 （retrieval_log），记录每次检索的分支大小、融合 top、精排 top 与耗时。

service.py:317 record_audit admin.py:278 audit query_log.py:23 retrieval_log

生成阶段还会记录 sql_audit 行（版本、用户、工具、SQL）， 所以「谁在什么时候让系统执行了什么 SQL」是有据可查的。

身份与脱敏这条链上另有四条：

action记的是
authz.deny执行期的拒绝：哪个数据源、哪张表、什么原因
authz.table_warnwarn 期放行了未声明的表：数据源 + 表名清单。门看见了越界并让行——比一次干脆的拒绝更值得留痕，也是「哪些表会被拒」唯一答得全的地方
authz.on_behalf_of谁发起了一次以他人身份的重放
masking.applied哪些字段被改写成哪种模式（不记值）
masking.bypass谁按原文读走了数据（持 pii scope 的那次）

「改写了哪些字段」与「谁看了原文」分开记，而不是合成一条：一次 bypass 的运行字段表是空的， 合并之后最该留痕的那次读取会表现成「这次没脱敏」。 applied 与「脱敏节点跑了但没改动」也不等价——前者说明结果里确实有被改写的列。

人在环：默认不执行

HITL 开启后，SQL 在执行前被拦下交给人确认。这里有一条贯穿全站的原则的又一次体现： 认不出来就拒绝。

hitl.py:45 未识别的载荷一律 hitl.py:80 hitl

恢复载荷解析不出来时，节点不会「当作批准」——它会明确拒绝执行并记录原因。 这个方向的选择很好理解：一个签名验不过的批准，比没有批准更可疑。

什么时候跳过 HITL为什么
配置里没开—
没有 SQL 可执行没什么可确认的
上游已经出错执行路径根本不会走
处于修正轮第一轮已经确认过意图了

定时任务走同一条路但自动放行——否则无人值守的任务会永远卡住。 这个区别写在调度器里，不在提示词里。
