安全边界

问数系统要执行模型生成的 SQL。这一页讲 Trove 怎么把这件事变安全： 只读的三层门、限流、加密、审计，以及几处刻意选择「失败时拒绝」而不是「失败时放行」的地方。

只读执行：三层门

「只允许 SELECT」这句话在三个不同层次上被检查，而不是只在一个地方：

层做法拦什么
① 关键词正则 廉价的首层筛查 明显带 DML/DDL 关键字的语句
② AST 防火墙 SQLGlot 解析成语法树后整树扫描 数据修改型 CTE、SELECT ... INTO OUTFILE 等伪装成 SELECT 的写操作
③ 执行器统一门 最终执行入口再查一次 任何绕过前两层的路径

guard.py:50 check_readonly guard.py:100 find_all registry.py:413 _guard_read_only

为什么必须做到 AST 级

正则挡不住这种：WITH x AS (DELETE FROM t RETURNING *) SELECT * FROM x。 它以 WITH 开头、含 SELECT，看起来人畜无害，实际在删数据。

要发现它只能真的解析成语法树，然后扫描整棵树的 DML/DDL 节点—— 而不是只看第一个词。

真正的边界在数据库侧

代码里对这一点写得很直白：真正的授权边界仍然是数据库侧的只读角色。 三层门是纵深防御，不是「有了它就可以给写权限」的理由。

给 Trove 一个只会 SELECT 的账号，是这里性价比最高的一件事。账号怎么建见 接入数据源。

限制值作用

试跑超时5 秒探测不该拖垮循环

gen_sql.py:592 PROBE_LIMIT gen_sql.py:594 PROBE_TIMEOUT_S gen_sql.py:797 CHECK_RESULT_LIMIT executor.py:36 timeout_ms

注意试跑超时（5s）与执行超时（30s）是两个不同的数。 一个模型自发的探测不该占用正式执行的预算，卡住它就该快速失败、换个思路。

自检：怎么确认那道边界真的在

「边界在数据库侧」这句话本身得有人验。启动时 Trove 会问每个数据源一句： 这个账号到底能不能写？结论会 WARN 到日志，并作为每个源的 readonly 字段出现在探活端点上。

它绝不「试写一条语句」

用一条「必然失败的写语句」来验证只读，是最容易想到也最不该做的事： 它「必然失败」的前提，正是「账号只读」这个还没有被证明的假设。 账号其实可写时，那条语句会真的写进去——一个探测变成一次生产写入。

所以自检只查权限表：MySQL/Doris 走 SHOW GRANTS，PostgreSQL 查 pg_roles / pg_class / table_privileges， ClickHouse 查 system.grants（含角色继承展开）。一个字都不写。

datasource/readonly.py 自检编排 core/types.py ReadonlyProbe

限流与配额

业务端点按用户限流，两个维度叠加：每分钟的令牌桶，加上每日总配额。 被限流拒绝的请求不计入日配额——这一点是对的， 否则一次突发会把当天的额度烧光。

维度默认关掉
每分钟请求30设为 0
每日配额300设为 0
登录尝试5 次 / 15 分钟环境变量调整

deps.py:193 check_api_rate config.py:180 api_rate_per_minute ratelimit.py:24 TokenBucket

限流是进程内实现。单实例部署下这是准的；多实例部署时每个实例各限各的， 实际额度会翻倍——这是当前实现的一个已知边界，需要严格限流时应在网关层再做一层。

认证与授权

鉴权是 fail-closed 的：没有认证组件时服务拒绝启动，而不是裸奔运行并打条警告。 这条设计在系统架构里也提到了—— 它是「宁可起不来，也不要静默地不安全」。

app.py:172 auth is None deps.py:73 get_current_user deps.py:137 require_scope

授权有两个层次，容易混淆，值得分清：

概念是什么用处
账号角色 admin 或非 admin 决定能不能进管理端
工具 ACL 角色 analyst（admin 隐含） 决定生成时能看见哪些 catalog 工具
数据源 grants 用户 ↔ 数据源的授权表 决定能问哪些源

analyst 不是一种账号角色——没有「analyst 账号」这种东西。 它是工具可见性的过滤键：授予后，生成节点里那几个能摸物理 schema 的工具才对这个人可见。

policy.py:68 Principal deps.py:156 require_datasource

数据源 grants 的语义是三值的，而且三值都落在安全的一侧： None（拿不到授权依据）拒绝一切；空集合只放行默认数据源； 非空集合是严格白名单。所以「忘了授权」和「读不到授权依据」都不会退化成放行。

判定只有一份实现

这套策略统一在 services/authz/policy.py，HTTP 侧与 MCP 侧都调它。 此前两处各有一份手抄，已经漂移过——同一个策略抄两遍就会有两套行为，这正是收口要解决的问题。

凭证与加密

数据源连接串里的密码在落盘前加密（TROVE_SECRET_KEY 作为密钥）。 加密值带 enc:v1: 前缀标记；没有前缀的是旧版明文， 读时透传、下次写时自动加密。

secrets.py:123 TROVE_SECRET_KEY secrets.py:39 enc:v1

这个「带前缀标记 + 向后兼容」的形态让迁移不需要一次性的批处理： 存量明文能继续用，随着配置被重新保存自然加密完成。

模型 API key 建议走环境变量或配置文件里的 ${ENV_VAR} 占位符—— 这样配置文件本身可以进版本库。详见配置参考。

审计

管理操作会写入审计日志，管理端有查询端点。另外，检索层有自己的查询日志 （retrieval_log），记录每次检索的分支大小、融合 top、精排 top 与耗时。

service.py:317 record_audit admin.py:278 audit query_log.py:23 retrieval_log

生成阶段还会记录 sql_audit 行（版本、用户、工具、SQL）， 所以「谁在什么时候让系统执行了什么 SQL」是有据可查的。

人在环：默认不执行

HITL 开启后，SQL 在执行前被拦下交给人确认。这里有一条贯穿全站的原则的又一次体现： 认不出来就拒绝。

hitl.py:45 未识别的载荷一律 hitl.py:80 hitl

恢复载荷解析不出来时，节点不会「当作批准」——它会明确拒绝执行并记录原因。 这个方向的选择很好理解：一个签名验不过的批准，比没有批准更可疑。

什么时候跳过 HITL为什么
配置里没开—
没有 SQL 可执行没什么可确认的
上游已经出错执行路径根本不会走
处于修正轮第一轮已经确认过意图了

定时任务走同一条路但自动放行——否则无人值守的任务会永远卡住。 这个区别写在调度器里，不在提示词里。
