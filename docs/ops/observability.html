可观测性

这一页回答两个问题：系统现在健康吗， 以及刚才那个答案是怎么来的。前者靠健康检查与指标，后者靠轨迹。

健康检查：三态，不是两态

探活端点返回三种状态，区分「完全不可用」与「部分降级」：

状态HTTP触发条件
unavailable 503 内部存储不可达——服务真的没法工作
degraded 200 存储正常，但某个数据源连不上
ok 200 都正常

app.py:256 health app.py:44 _HEALTH_PING_TIMEOUT_S

为什么数据源挂了不返回 503

一个数据源连不上，不该让编排系统把这个实例摘掉——其他数据源还是好的，而且这个数据源可能只是临时网络抖动。

所以它降级为 200 + degraded，把判断权交给监控侧。反之存储不可达是真的没法服务，必须 503。

探活本身有 2 秒超时——健康检查不该因为下游慢而挂住，那样探活会从「发现问题」变成「制造问题」。

Prometheus 指标

/v1/metrics 输出 Prometheus 文本格式。它是免鉴权的， 理由是单进程 serve 的计数不敏感，而抓取端通常不便于携带用户 token。

app.py:347 metrics metrics.py:160 render_metrics

如果部署形态会把这个端口暴露到不可信网络，那就应该在反向代理层收掉这个路径—— 这是部署决策，不是代码里的默认值能替你决定的。

轨迹：两种粒度

系统同时维护两份轨迹记录，用途不同：

本地 tracerun log
位置 {home}/traces.jsonl {home}/runs/{run_id}.log
粒度 结构化事件（run / step / llm / finish） 人类可读的详细过程
保留 最新 2000 行（超出丢最旧） 最新 50 个 run
用途 批量分析、程序消费 /trace 回放、排查具体一轮

local.py:24 MAX_LINES runlog.py:25 MAX_RUN_LOGS

两者都有界——这是刻意的。一个把磁盘写满的可观测性系统， 最终会变成一个可用性事故。丢最旧的是最简单的有界策略。

run id 被注入到日志上下文里，所以每行日志都带 [req=... run=...]， 可以直接 grep 出一轮请求的全部日志。results.jsonl 里的每条判定也带 run_id，从「哪道题错了」到「那一轮发生了什么」是一条可走的路径。

runlog.py:45 run_id_var logging.py:40 setLevel

回放一轮

/trace            # 回放最近一轮的完整轨迹
/trace list       # 列出可回放的轮次

trace_cmds.py:180 trace

Langfuse：可选的上报

配置了凭证时，同一批事件也会发往 Langfuse。启用条件是 两个环境变量同时存在，配置里另有一个总开关。

observability.py:40 langfuse_enabled observability.py:31 langfuse_trace_id

trace id 由 run id 推导（去掉横杠），所以两套系统里的标识是同一个—— 「本地日志里这一轮」与「Langfuse 里这一轮」不用做映射。

凭证缺失时是静默不启用，不是启动失败。理由是一致的： 追踪是增强能力，不该成为运行的前提。测试环境里相关环境变量会被主动清掉， 保证测试不试图外连。

事件从哪来：观察者中间件

追踪不在每个 LLM 调用点埋，而在 agent 循环的观察者中间件里。 默认有一个恒在的观察者，负责把事件分发到 run log 与 Langfuse。

agent_loop.py:222 _observers agent_loop.py:285 add_observer agent_loop.py:335 _trace_observer

这样做的直接好处是：新增一个可观测性后端不需要改任何调用点， 注册一个观察者即可。间接好处是「漏埋点」这类问题从根上消失了。

出问题时的排查顺序

现象先看哪
服务整体不可用 /v1/health 的状态与其中的存储 ping 结果
某个数据源问不出来 health 里的数据源检查段；再跑 check_drift.py
答案内容不对 先查 query_sketch 节点的输出——输出列往往是被计划定死的，而不是生成阶段选错的
想知道某一轮为什么这么答 /trace 回放，看模型当时拿到的上下文与工具返回
准确率整体下滑 回归门对比（评测与回归门），而不是逐个案例猜
一个具体的排查经验

输出列不对时，先看计划，不要先看生成的 SQL。用户消息里那句「Query plan (follow it…)」的权重高于系统提示里的规则——生成节点的行为是「照计划执行」。

所以计划里 answer_columns 写错了，生成阶段会忠实地把错误执行出来。去改提示词是白费力气。
