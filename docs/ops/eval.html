评测与回归门

问数系统的改动有个共同难题：你怎么知道这次改动没让系统变差？ 凭感觉不行，跑一次端到端评测很贵。这一页讲 Trove 用的第三条路： 纯文件的回归门——零 LLM、零网络。

三层结构

层件成本
录制与回放 trove/eval/replay.py 零
指标与对比 trove/eval/gate.py 零（纯函数）
端到端评测 scripts/eval_bird.py 花钱

设计意图是让绝大多数改动不需要走到第三层。 第一、二层是把「已经跑过的结果」变成可反复对账的数据。

录制与回放

跑一次真实评测时，每一轮的轨迹被录下来；之后就可以离线回放打分， 不调用任何模型、不连任何网络。

replay.py:104 score_replay replay.py:39 sql_exact_match

sql_exact_match 用的是 SQLGlot 结构级比较，不是字符串比较—— 大小写、空白、别名写法的差异不该算作不同。同理，一致性判断里 「可判定的 verdict」集合是唯一定义，被门与回放共用， 避免两处口径分叉。

replay.py:52 JUDGED_VERDICTS

回放产物落在 .trove/eval/replay.jsonl。

指标口径

指标怎么算
EX可判定条目里 MATCH 的占比
编译命中率带 compile_meta 的条目里 outcome 为 compiled 的占比
完成率最终交付了答案的占比
恢复率尝试过恢复的条目里成功恢复的占比
gold 精确匹配仅回放条目（有 gold_sql 的）
共识率 / 置信度可判定条目里多候选投票达成共识的占比，与平均置信度
平均重试每题平均重试次数（更低更好）
token 成本avg_tokens 与 total_tokens——只有带 token 记账的条目进分母
检索指标mrr / recall@k / ndcg@k / zero_recall——只在 scorecard 产物里出现

条目数 n 与可判定题数 n_judged 不参与判定： 它们是分母，不是成绩。只出现在一侧的指标进「无基线不可比」清单，同样不拦。

gate.py:117 metrics_from_entries gate.py:205 consensus_rate gate.py:254 n_judged gate.py:240 compare_metrics gate.py:310 render_report

每个指标都得声明「哪个方向是变好」

EX 涨了是好事，平均 token 涨了是坏事。所以指标被分成 HIGHER_BETTER 与 LOWER_BETTER 两个集合——没有这个声明，回归判定根本无法自动化。

这是「门」能成立的前提：「变差」必须是一个可计算的方向，而不是评审时的印象。

gate.py:36 HIGHER_BETTER gate.py:47 DEFAULT_TOLERANCE

容差：绝对量或相对量

指标在小样本上本来就会抖，所以对比带容差。容差可以写成绝对量（0.02） 或相对量（后缀 -r，如 0.10-r 表示允许 10% 的相对波动）。

token 成本这类量级跨度大的指标适合相对量——「涨了 100 个 token」在 1000 的基数和 10000 的基数下意义完全不同。

分母漂移会告警，但不会拦

gate.py:287 DENOMINATOR_DRIFT_WARN

如果两次运行的样本量差得太多（默认 20%），门会警告但不判回归。 这个区分很重要：样本量变化会让所有指标失去可比性，但把它当成回归拦住提交会误伤 （比如你只是加了几道题）。告警把判断权交回给人。

门消费哪三类产物

产物来源内容
results.jsonl eval_bird.py 逐题判定条目（含 run_id，可反查轨迹）
replay.jsonl offline_eval.py replay 回放记录
scorecard json tune_rrf.py / eval_hybrid_retrieval.py / eval_bird_retrieval.py / offline_eval.py replay --scorecard 检索与 RRF 指标；回放那条给的是评分指标（CI 用它重算冻结基线）

gate.py:346 load_entries eval_bird.py:117 RESULTS_PATH offline_eval.py:44 --scorecard

注意 scorecard 不是门的参数，而是上游脚本的输出旗标； 门统一通过 --baseline / --current 消费它们。 这意味着改检索参数也会被门拦住，不需要跑端到端评测。

冻结基线：门要有锚点才拦得住

回归门比的是「两个时刻」，所以仓库里钉着一份可复现的基线 （eval/baseline/）：questions.jsonl 是固定题集（每行带 qid、evidence、gold_sql）， results.jsonl 是这批题的历史判定条目，scorecard.json 是从后者算出并钉住的指标。conf/agent.yml 的 eval.baseline_path 默认就指向 eval/baseline/results.jsonl， 所以 --baseline 不填也有锚点。

eval_baseline.py check --require-full 校验这份基线还成不成立： 题集字段完整、qid 可对账、指标算得出来、没有冗余与重复判定。缺题在默认档只是告警， --require-full 把它升级成硬问题——CI 用严格档，因为「少了几题的基线」 会让所有比例悄悄换了分母。

eval_baseline.py:36 --require-full baseline.py:133 check_integrity conf/agent.yml:164 baseline_path

怎么用

uv run python scripts/eval_gate.py --baseline <旧结果> --current <新结果>
uv run python scripts/eval_gate.py ... --tol ex=0.02        # 覆盖单项容差
uv run python scripts/eval_gate.py ... --ignore avg_tokens  # 跳过某项指标
uv run python scripts/eval_gate.py ... --min-n 20           # 样本不足直接判为不可比
uv run python scripts/eval_gate.py ... --json               # 机器可读，供 CI 解析
uv run python scripts/eval_gate.py ... --ci                 # CI 模式
退出码含义
0全部指标在容差内（或无回归）
1存在回归——把改动拦下
2用法/输入错误、样本不足，或 --ci 下门未开启

eval_gate.py:47 --tol eval_gate.py:49 --ignore eval_gate.py:51 --min-n eval_gate.py:54 --json eval_gate.py:44 --ci

缺省参数从 conf/agent.yml 的 eval 段读， 所以本地不用每次敲一长串。挂到 CI 或提交前钩子上即可自动拦截回归。 --ci 是给自动化用的那一档：eval.gate_enabled 为 false 时它拒绝执行（退出码 2）——一个建好了却没开的门， 在流水线里会静默变绿，这比没有门更糟。

CI 里跑什么

.github/workflows/eval-gate.yml 每个 PR 都跑，四步全部零 LLM、零网络：

步命令挡什么
KB 禁背题 check_kb_anti_cheat.py KB 可检索示例里出现 gold SQL 的拷贝（模板命中即违规，人工条目命中只告警）
基线完整性 eval_baseline.py check --require-full 基线缺题、qid 对不上、指标算不出来
零 LLM 回放 offline_eval.py replay --input eval/baseline/results.jsonl 用当前评分代码重算那批冻结产物
门判定 eval_gate.py --ci --json 钉住的 scorecard vs 现算的：评分口径漂了、基线被误改了，就红

最后一步成立的关键是两边来自不同时刻：一边是仓库里钉住的 eval/baseline/scorecard.json，一边是用当前评分代码从冻结结果重算出来的。 同一个文件自己跟自己比恒等 Δ=0，那是在冒充回归门。

但要说清楚这四步挡的不是「模型变差了」：准确率回归要真库加模型， 仍然只能手动跑 eval_bird.py。这道门挡的是「锚点坏了」——基线缺题、 评分口径漂移、冻结产物被改。把这里的绿读成「准确率没问题」是误读。

禁背题那步不设开关：它零成本，问的也是「KB 还诚实吗」，与「模型变差了吗」是两回事； 其余三步只在 eval.gate_enabled（conf/agent.yml）为 true 时跑，置 false 会打印一行 skip notice， 而不是无声跳过。

eval-gate.yml:65 check_kb_anti_cheat eval-gate.yml:81 --require-full eval-gate.yml:97 --ci eval_gate.py:44 --ci

端到端评测：花钱的那个

不要随手跑

scripts/eval_bird.py 走完整反思管线、连真库、调真模型——它是计费的。仓库里对此有明确约定：没有明确指令不要启动评测运行。

日常改动应当先过回归门；只有在需要重新建立 baseline 或验证一个大改动时才跑端到端。

它的产物除了结果文件，还有一份 failures.jsonl 供 distill_lessons.py 蒸馏成教训草案（默认 pending，需人确认）。 逐题条目里带 run_id，可以据此找到那一轮的完整轨迹日志。
