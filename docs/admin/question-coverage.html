覆盖率体检

企业接入语义模型后最常问的一句话是：「我这批真实问题，系统现在能答多少？」 覆盖率体检把一批问题逐条送进生产链路的生成前段，给出编译级判定、覆盖率与缺口清单； 缺口可以一键生成待确认的语义草稿。它不执行 SQL、不读取业务数据、不判断答案对错—— 测的是「语义模型能否承接这些问题」，不是「答案准不准」。

它回答什么，不回答什么

管理台里已有两张与「覆盖」有关的报表，体检与它们的口径刻意分开：

你想知道用哪个口径
表 / 字段有没有建模 GET /v1/admin/coverage（治理覆盖） 资产视角：声明过没有
已经发生过的拒绝长什么样 审计日志 · 拒绝频率报表 事后视角：只统计问过的
这批还没敢问的问题，现在能不能接住 覆盖率体检 逐题视角：回放生成前段，按题判定
答案对不对 不在这页，也不在体检里 需要真实执行与金标准；体检不读业务行
为什么不做执行评测

执行评测要读业务数据、要金标准、要付费调用生成链；它回答的是另一个问题， 成本与隐私边界也完全不同。体检把范围钉在编译这一层： 语义模型能不能把问题编译成一条可交付的 SQL 骨架。这个边界让它可以安全地 跑一批真实问题——包括客户还不敢在对话里问的那些。

方法论：回放生成前段，绝不进入 gen_sql

每题的状态推进与生产查询图前段同构，顺序固定：

  1. 确定性意图分类（classify_intent）——不是查询类问题（元数据 / 写入 / 闲聊 / 纠错 / 确认）直接记 not_query，零模型调用，后面的节点一个都不跑。
  2. 时间解析（parse_date）——相对时间落成窗口；体检的「今天」固定为运行当天。
  3. 语义锚定（schema_linking）——确定性语义门：没有语义模型 → unmatched； 问题与语义资产零命中 → unmatched。零模型调用。
  4. 确定性快径（fast_match）——模板命中的问题直接记 certified，零模型调用。
  5. 计划抽取与编译（query_sketch）——唯一会调用模型的环节：把自然语言翻成计划， 随后由确定性编译器编译。重规划至多 2 次，即每题至多 3 次节点调用。

回放到此为止：不进入 gen_sql、不进入执行面、不读取任何业务行。 生成前段所需的 schema 元数据一次取好，语义层 provider 与生产启动走同一个构造工厂—— 「体检里能编译、生产里编译不了」这种两份构造漂移从一开始就不允许存在。

一个诚实的差异：生产图的 route_intent 有一次小模型调用，会结合会话历史做纠错与改写； 体检手里没有历史，用的是确定性意图分类。代价是最坏情况下多一次计划调用， 或把一个本可改写的问题记成 unplanned——方向是不虚报覆盖。

十种结局，没有第十一种

结局是一个闭集，分类优先级写在同一份纯函数里——报表、API 与前端都只消费它， 不各自发明口径。前六种计入覆盖率分母（evaluated），后四种单列：

结局含义进分母
certified确定性快径模板命中（零模型调用）是
compiled计划完整编译是
partial骨架存在，但仍有未覆盖组件（软 MISS 可保真交付）是
soft_miss软 MISS 且无拒绝：直通生成的未受保护缺口是
refused硬 MISS + 拒绝信号：语义模型的结构性缺口是
unmatched无语义模型 / 语义锚定零命中 / 无语义层是
not_query确定性意图不是查询（元数据/写入/闲聊/纠错/确认）否
unplanned计划校验丢弃 / 空计划 / 计划没表达可编译意图否
error超时 / 模型异常 / 节点吞异常 / 重规划不收敛否
skipped取消、运行超时或运行级失败而未处理否

两个覆盖率的分母都只含前六种结局：

  • 可确定性覆盖率 =（certified + compiled）/ evaluated ——不依赖生成兜底的覆盖；
  • 受治理覆盖率 =（certified + compiled + partial）/ evaluated ——骨架也计入（有未覆盖组件，但受执行前骨架保真校验保护）。

缺口率 =（soft_miss + refused + unmatched）/ evaluated； 拒答率、未锚定率、直通率各自单列。soft_miss 不并进拒绝—— 它仍可能由生成通道回答，算成缺口会虚低；unplanned / error 也不并进分母——它们不是「模型覆盖不了」，而是「这一问没判出来」。

「无样本」不是 0%

所有比率都是三键 {num, den, rate}；分母为 0 时 rate 是 null，页面显示「无样本 · 无法计算」而不是 0%。把无样本洗成 0% 是最容易被信以为真的假信号，这一条在纯函数、API 与页面三层都钉住。

未判出的比例超过总题数 20% 时，报告带 high_unmeasured 告警： 覆盖率只在可判定的题上有意义，先看「判不出来」的那一撮为什么判不出来。

成本前置：先看模型与调用量，再确认

体检的唯一付费环节是计划抽取。开始前页面会跑一次零模型调用的预检： 把确定性前段全部跑一遍，数出「哪些题不需要模型、哪些题需要计划抽取」， 再把模型名、模型来源与调用量估算摆出来——必须勾选确认成本才会创建运行。

一次体检的生命周期

输入有两种：粘贴（一行一题）与 CSV 上传。CSV 解析是纯解析、不落库， 并把「我们丢掉了什么」如实报出来：编码按 utf-8-sig → gb18030 → 替换字符回退； 自动识别表头（question / questions / question_text / query / 问题 等），识别不到就取第一列并告警；空行、逐字重复、超长行、截断都单独计数并展示。 一次静默丢行会让覆盖率分母悄悄变小，因此截断永远是可见的 （truncated=true + 告警）。

运行状态是一个闭集：

状态含义
queued已创建，后台任务尚未开始
running逐题推进中；进度 = 已处理 / 总题数
done全部题处理完（含单题 error）
error运行级失败（超时 / 调用上限 / 连续失败 / 内部异常）；已完成结果保留
cancelled用户取消；剩余题补 skipped
interrupted进程中断或心跳超时（stale）；剩余题补 skipped

取消是协作式的：置取消标记，循环在下一题开始前退出，不会打断正在跑的那一题； 已完成的结果全部保留。进程崩溃或重启后，心跳超过 5 分钟的 queued/running 运行会被 懒对账标成 interrupted，并补齐 skipped 行——状态端点绝不把 stale 行报成 running。 每题完成即落库并更新心跳，所以中断损失最多是当前这一题。

缺口清单与草稿门

逐题判定只回答「落在哪个结局」；管理者真正要处理的是缺口。报告按 (kind, reason, component) 聚合：同一个没声明的指标被多少道题用到、哪两张表的关系没声明， 一次看清。分组顺序与输入顺序无关（count 降序 → kind → reason → component）， 每组最多展示 3 条样例问题与 5 条候选规格。

缺口类别有七个：metric / field / value / entity / relation / dataset / other。 「可草稿」不由本页发明：只有语义草稿的唯一候选权威 （candidate_specs）给得出规格的缺口才标 draftable； 关系与数据集类缺口只给深链，绝不合成一条「看起来能点」的假草稿。

缺口类别一键动作落点
指标 / 字段 / 值 / 实体生成为待确认语义草稿本页勾选 → 语义工作台「待审批」
关系（扇出 / 基数 / join 二义 / 不可达表）去语义工作台手工声明/admin/semantic?ds=…&tab=datasets&q=…
数据集（无模型 / 未锚定）去知识库初始化或补建模/admin/kb?ds=…

草稿操作不信任运行时的预览：生成时用当前语义模型重新计算候选规格， 因此「运行时能草稿、现在已不可草稿」会如实落成 stale 或 not_draftable。 每条结果有五种状态：created / exists（按「种类 + 名称」幂等）/ invalid（校验不过，带错误明细）/ not_draftable / stale。 单次最多处理 50 条资产，超出的如实报 truncated，不静默截断。

草稿永远是 pending

体检从不确认草稿，也没有确认入口：产物只走既有写路径落成 pending， 仍需管理员在语义工作台逐条确认才生效。 自动内容不绕过确认门，这一条与知识库、Skills、决策规则的纪律同源。

对比上一轮：方向，而不是分数幻觉

每次运行都持久化，默认对比同一数据源上一轮完成的运行（也可以显式指定基线）。 逐题匹配用「归一化问题 + 出现序号」：同一个问题重复出现时按顺序配对，不相近的两轮各自记为 base_only / current_only。变化方向按覆盖序判定： certified=6 > compiled=5 > partial=4 > soft_miss=3 > refused=2 > unmatched=1； 两侧任一端不在覆盖序里（not_query / unplanned / error / skipped） 记为不可比，绝不硬判成变好或变坏。

对比页会核对两轮的语义模型 digest 与口径版本： 任一侧变过就显式提示——「这两轮之间语义模型有改动，差异不能全部归因于建模」或 「两轮用了不同版本的结局口径」。即使 digest 相同也不做强结论：计划抽取是有采样波动的， 单题在两轮间跳一个结局是正常现象，看分布与缺口，别看单题的一格之差。

存储与其它内部状态一样走统一的存储后端：默认 SQLite，设置 TROVE_STORAGE_URL 后为 PostgreSQL；迁移带版本、重跑幂等。服务在进程退出时显式 dispose()， 不留后台连接。

API 一览

全部挂在 /v1/admin/question-coverage，每条路由都要求管理员。 服务未装配时统一返回 503（coverage_not_configured），不静默降级。
