行动与审批

「问数 · 分析 · 决策 · 行动」的最后一腿。一条判定触发之后， 系统不会自己去改任何东西——它把「该做什么」冻结成一份提案： 载荷、依据、通道、风险都在里面，人批准了才外送，外送了还要回执。 而系统自身没有写回业务库的通道，这不是承诺，是结构。

为什么行动停在一份提案

判定可以自动，行动不行。两者出错的代价不是一个量级：一条判错的阈值， 最坏是多发一条通知；一个自动执行错的行动，改的是你的真实系统。 所以这里把自动化的边界画在「提案」上—— 机器负责发现和起草，人负责点头。

另一半是只读姿态。整个行动包（trove/services/action/）不导入数据源模块： ActionService 和 ActionDispatcher 的构造参数里没有连接器注册表， 数据库 SQL 守卫也不在它们的依赖里。ActionDispatcher 的全部输入是一个 通道名加一个载荷字典——它在物理上就无法写业务库，无论模板写了什么。 这条边界不靠约定维持：一个守卫测试直接对着源码断言「这个包没有碰连接器的路径」， 将来哪次编辑伸手去拿连接器，会在测试里响亮地失败，而不是在评审里被悄悄放过。

一条提案的生命周期

八个状态，一条单向街。能「往回走」的只有失败后的显式重试与取消， 其余每一步都是一次留痕的状态迁移：

状态含义还能做什么
pending待批准；载荷此刻已定稿批准 / 驳回 / 撤销；到点后过期
approved人工批准，尚未外送外送 / 撤销；MCP 客户端可拉取并签收
dispatched通道已接受（HTTP 2xx），尚无回执签收；不再可撤（已出楼）
delivered回执到达——对方确实拿到了终态
failed外送失败，原因在原行上显式 retry（有次数上限）
rejected / cancelled / expired人工驳回 / 撤销 / 超时清收终态

载荷创建即定稿

提案一出生，出站消息的字节就确定了——渲染发生在创建时， 之后不再重渲染。批准的是哪段文字，送出去的就是哪段文字；如果外送时才渲染， 一条被编辑过的规则或模板就能改掉一份已经批准过的消息， 而那正是审批这一步存在的意义。

发出的信封里还带一个 _trove 块：提案 id、幂等键、数据源、规则、模板、 风险、批准人、外送时刻。收件方据此在自己的侧边去重与归因——重发同一份不会变成两条行动。

同一触发，只提案一次

判定任务会重跑——手动重跑、调度推进两次、崩溃后重试——但同一场触发不该 产出第二份提案。幂等键是 sha256(rule_id | rule_digest | anchor_date | template | params)： 同一条规则、同一版本、同一个锚定日、同一个模板 → 折叠成一份；规则改过（摘要变了） 或换了日子，才算新的触发。刻意不把数字算进去—— 重跑时数据略有变化仍然是同一场触发，按数值做键会让每个 tick 都喷一份提案。 去重检查发生在渲染之前：重复的那次是廉价空操作，而不是一次「模板坏了」的假故障。

模板：组织自己的响应资产

规则说「当这个触发时，组织的响应是模板 X」。模板是一份 .trove/actions/<name>/action.yml——和 Skills 同一套 草稿 → 管理员确认门禁：未确认的模板不能被规则引用， 规则保存时的资产 lint 会直接拒绝。

模板是数据，不是代码，也不是提示词。它点名一个通道 （如 ops-alerts，绝不是裸 URL——URL 与密钥住在部署配置 agent.action.channels 里，模板可以被人审阅而不携带凭证）， 并给出一段带 {{变量}} 洞的 JSON 载荷。创建时先按样例变量试渲染一遍： 写错的变量名或 JSON 语法错误是写给作者本人的一个 400， 而不是规则第一次触发那个晚上的惊喜。

字段说明
action_typenotify（告警形状）/ webhook（载荷原样）
target.channel点名通道；resource 是可选的自由标签（如房间名），只给人看，不参与路由
risklow / medium / high
approvals_requiredv1 只支持 1；其他值在创建/读取时被响亮拒绝（一个「2」表现得像「1」是最糟的组合）

注入扫描：报告，不阻断

确认一份模板时，载荷文本与批准人看到的标签会过一遍注入扫描， 命中项返回给人看，但不拦截——与 Skills 同一款纪律。 拦截会毁掉作者本来就要的内容；沉默则会让管理员确认了自己没读过的东西。

两道门，加一个总闸

从「规则触发」到「消息出楼」之间站着两个互相独立的门，加一个部署层的总闸：

门在哪拦什么
模板门 模板服务 + 规则资产 lint 未确认的模板不能被规则引用；引用一个不存在或未确认的模板，规则保存不下来
审批门 提案状态机 提案以 pending 出生，只有人的 approve 能把它变成 approved——而 approved 是 dispatch 唯一可用的起点
总闸 agent.action.enabled 部署配置，默认 false 关着时 propose 与 dispatch 两个往外走的方向都被拒；批准 / 驳回 / 撤销 / 过期 / 回执与模板管理照常可用——可以先备好模板、清掉积压，再决定开不开外送

行为开关里最要防的是「关着，但看起来像开着」。所以关闸时的 dispatch 是抛错拒绝，不是静默跳过——这是全系统唯一一处「什么都没发生」与 「消息已送出」绝不能混淆的调用。

规则侧的对应字段是 action.autonomy——只有两个取值，且刻意没有 「auto」：notify_only（响应就是那条通知本身，永不离开系统） 与 propose（可以生成提案，但仍要人批准）。规则还可以写 recommendation（人写的「该怎么办」，随提案进入批准人的视野）与 driver_dimension（分析桥沿哪个维度找主因）。lint 会提醒： 声明了 action 却没写 recommendation，批准人看到的就是一段没有理由的模板。

失败是响亮的

外送失败在这里不吞——与定时任务的告警路径刻意相反。 告警路径失败可以静默：告警会重复，下一个 tick 会再投一次。 行动不会重复：它对着一场具体的触发被批准了一次。所以一次失败的 dispatch 会 把提案置为 failed、写下一行带错误的投递记录、并出现在管理端的待办列表里； 再试一次是一次显式的 retry，且受 max_attempts（默认 3）约束。

通道本身也是「失败即结果」：未配置的通道名不是异常，而是一次失败的投递—— 通道名打错、URL 不合法、网络超时，都是落在提案与投递记录上的可读事实。 每次投递记录带 HTTP 状态与一段有上限的响应摘录（512 字符）： 足够调试一次拒绝，小到恶意或话痨的端点点不满存储。

拉通道：MCP 与 webhook 并列

外送不是只有「推」一种姿势。已批准且未过期的提案同时出现在 MCP 侧的 trove://proposals 资源里，客户端可以list_proposals 看清单、fetch_proposal 取那份被人批准过的载荷、做完之后 ack_proposal 签收（幂等——已签收的再签是空操作）。 签收即 delivered：一个拉取了已批准提案并回执的客户端， 就已经收到它了，与 webhook 是否推过无关。

这条通道有一条刻意的边界：MCP 只能看和签收，不能批准。 批准 / 驳回 / 外送都是人在管理台做的决定——机器通道不投票。 提案清单也按数据源授权过滤，「取不到」与「没授权」返回逐字相同的一句话： 拒绝不能变成一件存在性预言机。

审计轨迹：谁批的、何时发的、对方收没收到

每一次状态迁移都写一行 approvals（追加式，含操作人、动作、备注、时间）， 每一次外送与签收都写一行 deliveries（通道、HTTP 状态、响应摘录）。 签收也写进同一条投递轨迹，而不是在别处立一个旗标—— 回执与投递是同一件事的两半。再加管理端 API 的 action.* 审计行， 「谁在什么时候批准了哪一份、发了几次」在提案存储之外也有答案。

在管理台里

管理台的「行动」页有两个页签：模板（草稿确认门禁、通道名、 风险级别、命中注入扫描的报告、试渲染预览）与提案 （按状态过滤的列表、待办计数、以及逐条的批准 / 拒绝 / 外送 / 重试 / 确认回执 / 详情）。 详情抽屉里是提案全文加它的完整审计轨迹。行动层未启用时，页面顶部有醒目的 「已停用」横幅——列表照常可读，外送按钮背后的那一步会被服务拒绝。

提案的来路在「判定规则」页里：一条规则声明了 action 之后， 它的每次触发都可以在这里看到「提案了没有、批没批、发没发出去」。
