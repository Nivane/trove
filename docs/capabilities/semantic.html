语义层

数据能力的第一组。语义层回答的是： 一句话问题里哪些部分可以被权威地翻译成 SQL，哪些不能。 能翻译的部分不交给模型，不能翻译的部分明确说出来——这一页讲这套判定是怎么做的。

语义层的职责边界

语义模型存在 semantics.yml 里，采用 Apache OSSIE 核心规范的 semantic_model 结构（datasets + metrics，表达式按方言声明、表名限定）。 这是唯一被读取的格式：更早的扁平 terms: 写法已经不再读取—— 解析出来是零条，只留一条迁移警告。手里有旧格式的库，重跑一次 /kb init --overwrite 再生成即可。

先把一件事说清楚，因为这里最容易误会：语义层不是「更好的提示词」。 提示词影响的是模型输出的概率分布，而语义层做的是编译——把结构化的计划 确定性地翻译成 SQL，同一份计划永远得到同一条 SQL。

语义层做语义层不做
指标口径 把指标展开成它声明的表达式 猜一个没声明过的指标该怎么算
表关联 按声明的 relationship 求 join 路径 在两条都说得通的路径里选一条
行集正确性 识别会放大/复制行的 join，拒绝它 生成一条「大概对」的 SQL 让人自己发现
权限 把声明的行过滤谓词注入每个引用该表的查询 替代数据库侧的只读角色

语义模型的结构

语义模型由四类构件组成。它们的关系是：数据集提供表，关系提供边， 字段提供可用的列，指标提供算法。

models.py:242 SemanticModel models.py:59 SemanticMetric models.py:96 SemanticField models.py:142 SemanticRelationship

关系上有一个字段值得单独说：fan_out。它在模型里是显式声明的， 而不是运行期推断的——因为「这条边会不会放大行数」是关于业务的判断， 数据库的元数据里没有这个信息。

models.py:169 fan_out models.py:168 cardinality

编译：三态产出

编译入口有两个。新契约返回三态（成功 / CompileMiss / PartialCompile）， 旧契约为了字节级向后兼容只返回两态（任何 MISS 都返回 None）：

compiler.py:2664 compile_detailed compiler.py:2642 compile_from_plan compiler.py:1727 SemanticCompiler

PartialCompile 是这套设计里最特别的一个产物。它同时携带三样东西： 已经编译好的骨架 SQL、一份交给生成通道的交接契约、以及未解析组件的清单。

compiler.py:1128 PartialCompile contract.py:160 PlanContract contract.py:214 render_contract

契约的用途不是「描述」，是「约束」

契约会被渲染成一段文字注入生成提示，但它的作用不是告诉模型「我们做了什么」，而是划定不许改动的部分。模型补完的 SQL 事后要按同一份契约校验。

硬与软的完整判据

分类的权威是这三个集合。每条 reason 落在哪个集合里，是从「放行它会不会产出一个错的数」推导出来的：

compiler.py:1150 MISS_REASONS compiler.py:1191 HARD_MISS_REASONS compiler.py:1210 SOFT_MISS_REASONS compiler.py:1237 is_hard_miss

硬 MISS 逐条

reason触发条件放行会怎样
no_plan_or_matched 没有查询计划、没有匹配到表，或者压根没有语义模型——编译无从开始 没有可编译的起点：放行等于让后面每一步都建立在猜测上
fan_out join 路径上存在声明的行倍增边 被聚合的明细行被复制，金额类指标成倍放大
unknown_cardinality 边的基数未声明，无从判断是否倍增 不确定就等于有风险——宁可拒绝
ambiguous_join_path 两表间存在多条连通路径，或显式 joins 不构成连通树 选错路径 = 用另一个口径算，结果看着正常但是错的
unreachable_table 投影表守卫：产物引用的表不在连接树内 SQL 引用了一张没被 join 进来的表
table_not_allowed 引用了数据集白名单之外的表 越界访问
derived_cycle / derived_depth / derived_unresolved 派生指标成环、展开超过深度上限、或定义悬空 展开它没有终点，或展开成一个空表达式
metric_anchor_unmatched 指标的锚定表不在本次匹配到的表里 生成的 SQL 会引用未覆盖的表
limit_without_order 要求 LIMIT 但没有排序依据 取到哪些行是不确定的
nothing_compilable 兜底：一个成分都编译不出来 —
guardrail_rejected 编译产物未通过语义侧护栏校验 产物本身越界

判定 fan-out 的地方分两处：显式 joins 走 guard_edge_cardinality， 自动寻路走 BFS，路径上遇到倍增边即拒绝。派生指标的展开深度上限是 5 层。

软 MISS 逐条

软 MISS 的共同点是：结构是清楚的，只是某个词/值/口径没登记。 这类问题可以带着缺口继续走，因为缺口的位置是已知的。

reason缺什么
no_metric_match问题里的聚合意图没有对应的已声明指标
bad_time_grain / time_field_not_declared / time_field_not_temporal时间分桶的粒度未声明、字段不是时间类型
unresolved_answer_column要输出的列没有在语义模型里登记
unresolved_filter_field / invalid_op / missing_filter_value过滤字段未声明、算子不适用、比较值缺失
enum_value_unresolved用到了某个枚举值，但它不在该字段的已声明取值里
having_metric_unknown / having_without_aggregationHAVING 里点了一个没有声明的指标，或者压根没有可据以过滤的聚合
time_grain_without_aggregation要按时间分桶，但没有可以分桶的聚合
analysis_*（六条，见下）窗口 / 分析函数这一段没解析出来

软 MISS 一共 18 条，表里按「缺什么」归了类；完整的闭集在 SOFT_MISS_REASONS 里，新增 MISS 分支时必须归入软硬两边之一。

窗口与分析函数

语义计划里可以带一段 analysis，编译期展开成窗口函数。支持六种： share（占整体比例）、running_total（累计）、 mom / yoy（环比 / 同比增量）、pct_change（变化率）、 rank（排名）。它们都是单度量的——窗口计算围绕一个度量展开， 所以计划里必须恰好有一个聚合度量投影。

reason缺什么
analysis_unsupported_type类型不在上面六种里，或写成了一个数组 / 空值
analysis_metric_unknown点名的度量没声明，或聚合度量不止一个
analysis_partition_unresolved分组维度（PARTITION BY 的依据）没解析出来
analysis_order_unresolved排序依据没解析出来——累计 / 环比 / 同比没有它就无从下手
analysis_time_required这类分析必须沿时间轴走，但计划里没有时间维度
analysis_invalid这段 analysis 的形状本身不对（不是对象、内层 SQL 解析不出来）

注意这些全是软 MISS：窗口那一段交回生成通道按计划文本补齐， 内层的分组与过滤仍然由编译器权威产出。缺一段不该让整条查询停摆。

收集软 MISS 的入口是 _record_soft——它只记录，不中断编译， 所以一次编译能把所有缺口都收集齐，而不是修一个报一个。

compiler.py:2652 _record_soft compiler.py:3344 PartialCompile

一个准确度上的细节

is_hard_miss 是 reason → 软硬分类的权威判定函数，但运行时的路由并不是靠调用它决定的，而是靠编译产物的类型：拿到 CompileMiss 就走拒绝路径，拿到 PartialCompile 就走骨架路径。

这个区分在写扩展或调试时很重要——想知道「为什么这次拒绝了」，看的是产出的类型与它携带的 reason，而不是去追 is_hard_miss 的调用点。

骨架保真校验

软 MISS 放行之后，生成通道会拿到骨架和契约去补全 SQL。执行之前有一道校验， 它比对的是三样东西：join 边、WHERE 条件、分组宽度。 投影列不参与比对——补全本来就可能调整输出列，那不是破坏契约。

compiler.py:4053 skeleton_preserved compiler.py:4132 compiled_sql_matches execute_sql.py:177 skeleton_preserved

校验有两种失败方式：SQL 解析不了，或者解析出来发现丢了骨架里的东西。 两种都会把这一轮打回重生成，而不是带着一个已破坏权威性的 SQL 去执行。

execute_sql.py:182 _compile_drift_failure

行级安全：在编译期注入

数据集可以声明一个 row_filter——一个恒真的布尔 SQL 谓词。 编译时，每个引用该数据集的查询都会被注入这个谓词到顶层 WHERE。

models.py:193 row_filter rls.py:99 inject_row_filters rls.py:75 render_row_filter

fail-closed，不是 fail-open

注入失败时（谓词渲染不出来、SQL 结构不认），系统放弃这条路径而不是跳过过滤。快径命中模板后也要单独注入一次——它不经过编译器，所以必须自己补上这一步，注入失败就退回编译路径。

rls.py:30 RLSInjectionError fast_match.py:502 rls_applied

但这份机制有一条明确的边界，不该被误读成安全保证： 声明层的行过滤不替代数据库侧的只读角色。它的作用是让「同一个语义模型下的所有查询」 口径一致，而不是防止有人绕过 Trove 直接连库。

声明式 API 的严格契约

如果是通过声明式 API 调语义层（而不是走对话工作流），契约会变得更严格： 遇到 PartialCompile 直接返回 422，而不是降级补全。

query.py:180 compile_detailed query.py:185 PartialCompile

理由很直接：程序调用方拿到一个「补全过的」SQL，它无法判断哪些部分是权威的、哪些是模型填的。 而对话场景里用户可以看见解释、可以追问。所以同一个语义层，两种调用方，两套契约。
