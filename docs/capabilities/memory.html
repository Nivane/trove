记忆子系统

把散落在各处的记忆收成一个门面：情节、偏好、画像、生命周期。 它的核心约束只有一条——自动写入不越过人工确认， 但「事实记录」与「可复用知识」被区别对待。

为什么需要一个门面

记忆不是一种东西。至少有三类，它们的写入时机、可信度、失效方式完全不同：

层记什么可信度谁能改
情节 问过什么 → 生成了什么 SQL → 判定结果 → 改过几轮 事实记录，不声称正确 系统自动
偏好 用户表达过的长期口径与习惯 模型抽取，可能抽错 高置信直接生效，低置信待确认
知识 可复用的示例与教训 必须人工确认 草稿自动、生效靠人

在此之前这些记忆各写各的，读的地方也各取各的。门面 service.py:41 MemoryService 把它们收成一个读写口，统一失败不阻塞查询：任何一次记忆读写出问题， 都只落日志，不影响这次问答。

service.py:15 New automatic memory

「pending 或自包含」不是「一律 pending」

源码的自述比常见转述更精确：自动写入的东西要么是 pending 草稿（等管理员确认），要么是自包含记录（只对产生它的那个用户可见、不会被当成知识复用）。

情节记忆属于后者——它是「当时发生了什么」的事实记录，按 (数据源, 用户) 隔离，不参与跨用户的知识复用。把它和「可复用的示例/教训」混为一谈，会得出「记忆子系统会自动污染知识库」的错误结论。

召回：词面与语义的 OR 门

检索走两路并联：词面相关度与向量余弦各设一道门槛， 任一门通过就召回。这个 OR 而不是 AND 的选择是有意的—— 两种失败模式不对称：漏掉一条有用经验，比多带一条不相关经验代价大得多。

总分是 0.6·余弦 + 0.4·词面，再加一个温和的最近度衰减—— 30 天半衰，权重只有 0.2。衰减刻意做得很轻：问数场景里，半年前的一条正确口径 通常仍然是对的，不该因为「旧」被埋掉。

进上下文时是什么

召回的情节作为 episodes 块进生成上下文，但成功的和失败的用法相反： 成功的 SQL 作为少样本锚点，失败记录连同修正历史作为反例。只放成功的会让模型看不到边界， 只放失败的会让它学不到正确写法。

偏好：会话压缩时抽取

偏好的抽取时机是会话压缩，不是每一轮。理由很实际： 一次性请求和闲聊里根本没有持久偏好，只有一段对话的全局特征才能暴露「这个人习惯怎么看数」。

草稿存在 ~/.trove/memory/preferences.sqlite，由 LLM 抽取 （提示词模板 memory/preference_extract.{en,zh}.j2，跟随提问语言）。

preferences.py:243 extract_and_store preferences.py:44 HIGH_CONFIDENCE

两条出路，按置信度分

  • 置信度 ≥ 0.9 —— 直接写进该用户的 user_facts，下一轮就生效。
  • 低于阈值 —— 落成 pending 草稿，等管理员在 /admin/memory/preferences 确认或拒绝。

为什么高置信可以直通？因为 user_facts 是按用户隔离的： 一条「我习惯看日均值」抽错了，影响的是这个人自己的下一次提问，不会污染别人， 也不会进知识库。这是「自包含」的一个实例——风险范围决定了要不要人工确认。

抽取前还有一道噪音过滤：闲聊、一次性请求、不含持久口径的句子被直接丢掉， 而不是低置信存起来。存下来只会让待确认列表变成噪音。

自动晋升：默认关的那一档

这是整个子系统里唯一「自动把草稿变成生效知识」的通道，因此默认关闭。 它的机制是一个证据累加器：某条 pending 教训被反复印证，置信度就会涨， 越过阈值后自动确认。

表里只有两条，是按「真的有产出方」筛过的：曾经还有一条 lesson_reuse_pass（教训被复用且当轮成功），但没有任何代码产生这种证据， 且与 repeated_correction 语义重叠（同一件事可能加两次分），已删。 登记一个没有产出方的证据类型，等于给这条通道留一个永远为 0 的加数。

教训在 lessons.yml 里有两种写法：失败蒸馏与人工追加按 pattern，用户投票按 question。证据的匹配键因此 两者都认，检索文本也把 question 计入——否则投票教案的相似度 恒为 0，票数加权会乘在一个零上。

别把它改成自动注入

「让记忆自动生效、不用人工确认」看起来是个明显的改进，实际上会把知识库变成模型输出的回音室——一旦某条错误教训被自动确认，它会持续影响后续所有生成，而且没有人知道它是什么时候进来的。

情节记忆是例外不是漏洞：它记录事实、按用户隔离、不参与知识复用。这条边界值得保持。
