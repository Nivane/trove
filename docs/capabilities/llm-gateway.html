LLM 网关

全系统只有一个地方直接跟模型说话。工具治理与 agent 循环都建在它上面。这一页讲它管什么、 模型怎么选、以及为什么它要暴露三种不同的调用形态。

为什么要有一个网关层

底层是 litellm，也就是说「支持哪些模型厂商」这个问题大部分被 litellm 回答了。 网关层存在不是为了再包一层，而是为了收口四件散在各处会出事的事情：

收口的事不收口会怎样
模型选择 各节点各写默认值，改一次模型要改十几处
凭证解析 API key 散在代码与配置里，容易进版本库
token 用量 预算控制（见下）没有数据来源
追踪 每个调用点都要自己埋点，必漏

gateway.py:52 LLMGateway

模型选择：三级优先

选择顺序是：命令行 --model > 项目配置 conf/agent.yml > 用户配置 ~/.trove/conf/agent.yml。前者用于临时实验， 后者用于个人偏好，中间那个是项目约定。

配置里通常有两个模型位：一个主力、一个快速档 （target 与 model_fast）。 分档的意义是让便宜的操作不要用贵的模型——比如某些只需要判断「这是不是一句问数」的地方。

providers 与凭证

providers 是一个列表，每项可以带自定义的 api_base—— 这是接私有部署或代理网关的入口。其中的凭证字段支持 ${ENV_VAR} 占位， 在加载时展开成环境变量值。

gateway.py:99 set_providers config.py:337 resolve_env_vars

占位符不是语法糖，是防泄漏机制

写 api_key: ${DEEPSEEK_API_KEY} 而不是把 key 直接贴进 YAML， 意味着这个文件可以安全地进版本库。配置文件一旦可以被提交， 「配置漂移」这件事才有办法被 review。

providers 为空时 litellm 照常回落到环境变量（如 DEEPSEEK_API_KEY）， 所以最小配置下你只需要 export 一个 key。

方法用途返回
chat 最常用：给提示，要文本 字符串
chat_full 需要工具调用能力时 内容 + 工具调用 + 尽力而为的 token 用量

gateway.py:105 chat gateway.py:187 chat_full gateway.py:277 chat_stream

chat_full 的用量是「尽力而为」的：不同厂商返回的用量字段并不统一， 拿不到时它不会报错。这一点在下游是有影响的——token 预算因此是一道软闸门， 不是精确计费器。

测试模式

网关可以带一个 mock_response 构造。设了之后，所有调用直接返回这个字符串， 不碰网络、不需要任何 key。

gateway.py:72 mock_response

这个模式是仓库「零 key、零网络、全 mock」测试约束的支点：整套 3700+ 测试 跑起来不产生任何 API 费用，也不依赖外网。没有它，CI 要么花钱要么不可靠。

工具注册表

工具不是散装函数，而是注册到一张表里，每项带一份声明： 名字、说明、参数 schema、所需权限、对哪些角色可见。

agent_loop.py:138 ToolSpec agent_loop.py:206 ToolRegistry

注册表在把工具列表交给模型之前按角色裁剪。越权的调用不会返回 「权限不足」，而是被折叠成「未知工具」——模型于是换一条路，而不是开始试探边界。 这个设计在工具治理里有展开。

agent_loop.py:519 visible_to

catalog 工具是「生成辅助」，不是「语义边界」

后三个工具让模型能以只读方式摸到物理 schema。它们存在的理由是： 值确认、结构懒加载、执行计划——这些确实需要看真实数据库。

但它们不参与可答边界的判定。边界由语义层说了算， 模型能看见物理表不等于它可以绕开语义模型去查。这两件事在实现上分开，是刻意的。

追踪

追踪在 agent 循环的观察者中间件里发生，不在每个调用点。 默认有一个恒在的观察者，把事件写进本地 run log；配了 Langfuse 凭证时， 同一个观察者再往 Langfuse 发一份。

agent_loop.py:361 run_agent_loop observability.py:40 langfuse_enabled observability.py:62 build_callback_handler

Langfuse 的启用条件是两个环境变量同时存在 （public key 与 secret key），配置里只有一个总开关。这样凭证缺失时是静默不启用， 而不是启动失败——追踪是增强能力，不该成为启动的前提。

trace id 由 run id 推导而来（去掉横杠），所以「按 run_id 找这一轮发生了什么」 在这两套系统里是同一个标识。详见可观测性。

observability.py:31 langfuse_trace_id
