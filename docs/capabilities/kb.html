知识库

语义层负责编译，知识库负责喂给它原料：指标口径、字段含义、枚举取值、 可复用的问答对、以及踩过的坑。这一页讲这些原料从哪来、怎么被检索到、以及为什么不能自动写进去。

五个文件，按「谁能写」分工

KB 的形态是一组 YAML，人可读可改，也是唯一真源。运行时另有一份 SQLite 镜像 （kb.sqlite，带 FTS5 虚拟表）——但镜像只服务检索， 删掉它可以从 YAML 重建，反过来则不行。

文件承载什么写入方
schema_notes.yml 表/列注释、枚举取值、统计画像 /kb init 起草，人可改
semantics.yml 语义模型（数据集 / 指标 / 字段 / 关系） /kb init 起草，人审
examples.yml 问答对（example）与模板（template） /kb init + /kb learn + 反馈回写
rules.yml 生成时必须遵守的规则文本 纯人工——代码里没有任何写入器
lessons.yml 失败模式与规避方法 蒸馏/反馈路径懒创建，两档确认

service.py:3 human-editable service.py:488 _parse_file merge.py:54 纯人工文件

为什么 rules.yml 要「纯人工」到这个地步

合并逻辑里对它的处理是原样保留，没有任何生成器会产出它。这不是疏忽，是分工：schema_notes 与 semantics 描述的是数据长什么样，可以从库里探测出来；rules 描述的是组织要求怎么算，库里没有这个信息。

把它交给 LLM 起草，等于让模型替组织定口径——那是它不该有的权力。

/kb init：能确定性生成的才生成

初始化一个数据源的 KB，走的是一条确定性优先的流水线。 顺序上先做不花钱的部分，再让 LLM 润色：

  1. 读活库 schema（表、列、类型）。
  2. 没有 LLM 凭证时的降级路径：只写一份 schema_notes.yml 骨架并返回提示，让人补注释后 /kb reload。
  3. 枚举采样与列统计画像（这一步会真的查库）。
  4. LLM 起草表/列注释。
  5. 确定性生成词表与模板——generate_terms / generate_templates。
  6. 合成示例，生成语义模型结构。
  7. LLM 起草同义词与描述。
  8. 原子写盘：三个文件连续写、中间不 await——避免留下写了一半的 KB。

init_pipeline.py:311 init_kb deterministic_gen.py:205 generate_terms deterministic_gen.py:358 generate_templates semantic_gen.py:210 generate_semantic_document

产出的文件是三个：schema_notes.yml、semantics.yml、examples.yml。 rules.yml 与 lessons.yml 不在其中—— 前者的原因是上面说的分工，后者是反馈路径首次写入时才创建。

init_pipeline.py:308 INIT_FILES

防作弊约束的形状

这条流水线的产物边界，就是「什么算真实的准确率提升」的边界：凡是 /kb init 不能确定性生成的内容，手工塞进去都不算。特别是把评测集的 gold SQL 抄进 examples.yml——那不是系统变准了，是答案被泄露了。

相应地，模板快径也只用 kind='template' 的条目，因为那是确定性产物，人塞的东西进不了这条快径。

/kb learn：把一次好的问答固化下来

交互式的沉淀路径是半自动的：模型从上一轮对话起草一条示例（外加候选术语）， 把草稿展示出来，只有用户明确确认才写盘。

kb_cmds.py:49 _cmd_learn service.py:2128 append_example service.py:2136 append_term

注意这里的确认与后面的「两档门禁」不是同一件事：/kb learn --yes 是当下的人工确认， 写进去就是 confirmed；而自动回写的示例进来时是 pending，需要另一次确认。 区别在来源——人当场看过并点过头的，和系统自己觉得不错的，不该同等对待。

检索：先确定性过滤，再打分

检索的入口在图上（一次问答会并行取示例、教训、术语、指标、实体）， 每条通道内部都遵循同一条原则：先用确定性规则排除不可能的，再排序。

graphs.py:413 search_examples service.py:1411 search_examples service.py:1469 _rank_examples

最重要的那条过滤是表锚定：语义链接阶段已经算出了这个问题涉及哪些表 （matched_tables），那么一条示例如果提到了别的表，它就不该被检索到—— 哪怕文字上再像。这是一个纯确定性的判断，不依赖任何模型。

service.py:1492 keep service.py:395 _lesson_table_ok

排序分由几路信号合成：术语命中、标签命中、词重叠、表锚定加分， 再乘上聚合/日期模板的折扣（模板类示例的泛化性弱一些，不该压过具体示例）。 与检索通道给出的相似度做融合时，权重是 0.5——这个数字是刻意的中庸值， 因为确定性打分和向量相似度各有所长，谁压倒谁都不合适。

service.py:273 _score_example service.py:433 _fuse_extra_sim

教训的排序多两个因子：投票与时效。 一条被反复验证有效的教训应当排前面，一条很久没被触发的教训应当淡出—— 后者用衰减函数实现，而不是靠人工清理。

service.py:1649 _rank_lessons service.py:416 _recency_factor

镜像与 FTS

YAML 是给人读的，逐条扫描它做检索太慢，所以运行时维护一份 SQLite 镜像。 FTS5 虚拟表是 contentless 的——它只存索引，元数据列标为 UNINDEXED， rowid 与镜像表的主键对齐。

service.py:114 _CREATE_FTS service.py:1088 _ensure_mirror_schema service.py:874 _sync_file_fts

在 PostgreSQL 生产环境里，检索不走这条 SQLite 路径，而是切到 pg_hybrid 后端—— 切换逻辑见 混合检索。两者的分界点是配置与能力探测， 不是数据源类型。

取值画像：让「枚举」这件事有依据

很多问数错误来自取值层的误解：「华东区」到底是 '华东' 还是 'east'？ 状态字段有哪些合法值？这些不属于 schema，但决定了 SQL 里的字面量写什么。

画像流程对每个可疑列做一次取值采样，取 Top-K 高频值与频次，连同形状判断 （是枚举？是 ID？是自由文本？）一起合并进 schema_notes.yml 的 stats。

profiling.py:31 TOP_VALUES_LIMIT profiling.py:55 detect_shape profiling.py:195 _probe_top_values profiling.py:253 merge_into_stats

独立脚本 scripts/probe_enums.py 做同一件事，但带两道护栏： 行数上限与超时。因为「对一亿行的大表做全表 GROUP BY」是一个很容易写出来、 又很容易把生产库拖垮的操作。

enum_probe.py:25 DEFAULT_MAX_ROWS enum_probe.py:36 probe_enums

lint：把 KB 的问题在提问之前发现

scripts/lint_kb.py 是这个仓库里唯一一个专门挑 KB 毛病的工具。 它检查的都是「不报错但会一直悄悄降低准确率」的问题：

类别典型问题
静态 术语 mapping 引用了不存在的列；对 ID 类列写 SUM/AVG；示例 SQL 解析不了、引用了不存在的表、含写操作
静态 纯中文问题（英文检索不可达）；列描述为空；教训的 pattern 过长或 note 为空
需要活库 schema_notes 里声明的枚举值漏了库里真实存在的值（如 loan.status 少了一个 'C'）
需要活库 库里存在但 KB 完全没记录的列

lint_kb.py:47 check_enums lint_kb.py:75 check_undocumented_columns

最后一条尤其值得注意：漏掉一个枚举值不会让任何查询报错， 它只会让「状态 = C 的那批」这类问题永远算错——因为编译器认为 'C' 不是一个合法取值。 这类错误没有报错信号，只能靠主动比对发现。

两档门禁：pending 不进检索

所有自动写入的内容默认是 pending。读侧的过滤器是硬的： 待确认的示例直接跳过，教训列表默认只返回 confirmed。

service.py:570 pending 草稿不参与检索 service.py:1599 confirmed_only service.py:1689 setdefault

门禁档内容确认方式
同步确认 /kb learn 的草稿 用户当场看见并加 --yes
异步确认 自动回写的示例、蒸馏出的教训、自动偏好 管理端列表逐条或批量确认

service.py:1763 confirm_pending_lessons service.py:1837 confirm_pending_examples service.py:1899 reject_lesson

一条会咬人的约束：KB 语言要跟着问题语言走

这是一个实测过一次的定性结论，值得写在这里而不是埋在文档角落： KB 内容的语言应当与提问语言一致。用中文 KB 去回答英文问题时， 准确率会明显下降，而且主要缺口不在生成、在少样本检索的命中—— 检索不到对的示例，后面再强也没用。

这是设计约束，不是运行期检查

代码里没有任何地方会强制或警告语言不匹配。它写在约束文档里，靠使用者和 lint 的「纯中文问题」检查来兜。所以如果你换了提问语言，记得配套重建 KB。

相关但不同的一件事：scripts/check_kb_anti_cheat.py 会做三级比对（字符串归一化、语法树相等、字面量盲化后结构相等）来抓「模板抄 gold SQL」——它只查 template: true 的条目，因为人工确认的示例按设计允许接近 gold。
