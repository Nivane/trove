版本与兼容

Trove 里到处是版本：语义模型文档的格式、判定规则文件、迁移、缓存键、运行记录…… 它们分散在 YAML、载荷与迁移里，升级与回滚没有单一权威。 这页讲的不是「再发明一个全局版本号」，而是把每一处版本点登记下来—— 它由谁写、读到更新或更老的版本会怎样、有没有测试钉住—— 再用纯 AST 机检逼着新版本点必须登记。 不新增运行时门禁：注册表只描述与冻结现状，真正的行为门仍属于各自的模块。

问题不是「没有版本号」

代码库里从来不缺版本号；缺的是一次能答完五个问题的地方： 这个版本字段谁写？谁读？读到更新的版本拒绝还是透传？读到更老的版本迁移还是收养？ 有测试钉住吗？没有这张账，版本读错的失败方向大多是安静的—— 少读一列不报错，只是默默用了错口径；透传一个未来格式不报错，只是把不认识的内容当认识的处理。 安静的失败比响亮的失败贵得多。

勘察时最刺眼的证据不是缺登记，而是同一个版本字符串有三个独立写入点： 生成端写一份、格式化端写一份、变更暂存端再写一份。只要三处里有一处被改， 另外两处就会继续产出「看起来一致」的旧格式——这正是注册表要防的双源漂移。 所以本批唯一的代码改动是把 OSSIE_VERSION ossie.py:59 OSSIE_VERSION 收敛为单一权威，其余写入点全部改成引用它，输出逐字节不变。 注册表如果一边宣称「单一权威」一边留着三个写入点，就是自欺。

三原则：写端闭合、读端宽容、派生重建

原则含义为什么
写端闭合 一个版本只有一个权威常量；载荷里的字面量写入也必须登记；迁移版本与代码同一提交 双源漂移不会自己暴露——只有一处被改时，两边都「看起来对」
读端宽容 老版本能读就读（迁移 / 收养 / 降级），结构性不兼容才拒绝；「判不了」有自己的一档 升级不是全量重写；把可分析的老数据拒之门外是另一种损失
派生重建，不迁移 镜像、向量索引、派生产物：结构变了就重建，不写迁移步骤 迁移历史必须反映曾经发生过什么，不能反映现在配置成什么

第三条在存储层的落地最典型：KB 镜像版本由 _MIRROR_VERSION service.py:1220 _MIRROR_VERSION 守住——读到更新的版本就抛 StorageSchemaTooNew migrations.py:54 StorageSchemaTooNew （旧代码打开新库是最安静的一种分叉），而解决办法是删镜像重建，不是补迁移。 与之相对，真正持久化的结构迁移走 apply_migrations migrations.py:226 apply_migrations， 每一步单独幂等、失败不推进版本。

版本点分六类，不可混谈

版本字段的读法决定它的类别。把修订计数当兼容门，会让一次普通编辑变成拒绝服务； 把缓存键当持久化格式，会让缓存失效变成数据迁移。注册表用闭集 kind test_version_compatibility.py:50 KINDS 强制分类，每个版本点只能落一类：

kind是什么典型例子
schema持久化结构的迁移版本各 store 的 Migration(version=…) 序列
format持久化内容或载荷格式；读端可能拒绝判定规则文件、扩展包、OSSIE 文档、evalset
revision单调修订计数，不是兼容门技能条目的编辑版本
informational写入但无消费方分支运行记录的版本戳、工具协议字符串
cache_key派生缓存键，不持久化判定 / validator 的域版本映射
derived派生产物结构版本，重生即升级运行账本、KB 镜像

容错矩阵：更新与更老各是一句话

「读到更新的版本怎么办」与「读到更老的版本怎么办」是两扇门，不能合成一个布尔值。 注册表给每扇门一个闭集词汇——行为只有这些，写不出「大概兼容」这种中间态：

更新版本（newer）含义
refuse拒绝，响亮报错（结构不认识的形状绝不猜）
degrade降级继续：打标 / 缺省 / 用可解析部分，原因可见
fold_unknown未知值折回默认（只对非结构性字段）
rebuild派生产物重建
pass_through原样保留，不做解释（没有消费者需要判断）
cache_invalidate缓存键版本变化即失效重算
n/a不存在兼容问题（无读者分支）
更老版本（older）含义
migrate按版本链迁移到当前结构
adopt收养：老数据不改写，读时按老口径解释
rebuild派生数据重建（同上，不写迁移）
accept接受并补默认/升级写回
degrade老数据能读但不完整，标记降级
pass_through原样保留
refuse双向拒绝（值域本身只有一种合法形状）
cache_invalidate版本不同即不再复用
n/a不存在兼容问题

这里刻意不抄具体版本号：页面描述机制，注册表持有值。把数字写进文档， 下一次升版就会出现「文档说 4、代码说 5」的第二次漂移——文档只该回答「读到更新版本时的行为是什么」。

注册表：让「没登记」变成红灯

注册表本体是测试文件里的一组冻结字面量 test_version_compatibility.py:343 REGISTRY： 每个版本点一行（id、权威位置、冻结值、kind、更新/更老行为、证据节点、可选缺口）。 它与代码的关系是双向精确：代码里发现一个版本常量而注册表里没有 → 红； 注册表登记了而代码里找不到了 → 红；两边都在但值不一致 → 红。 证据不是自由文本，而是 pytest node id——静态校验存在性，改/删被引用的测试会响亮变红并指名该改哪一行。

四个检测器都是纯函数，只吃源码字符串或既有分类表，不碰磁盘、不 import 被测模块 ——与其它架构注册表同一姿态（棘轮，不是沙箱）：

检测器扫什么为什么必须机检
module_version_constants test_version_compatibility.py:103 module_version_constants 模块体的版本常量（__version__、全大写含 VERSION、映射形态） 新常量最容易「顺手加一个」；显式排除表让 MAX_SQL_VERSIONS 这类上限不误报，且排除必须写理由
literal_version_writes test_version_compatibility.py:202 literal_version_writes 载荷里的 version / record_version 常量，含下标赋值 字面量写入绕开常量；动态值（preset.version）不误报，只认常量
migration_versions test_version_compatibility.py:217 migration_versions Migration(version=…) 的最大版本；非常量版本直接报错 迁移盲区是静默的：漏一步不报错，只是老库升不上来
store_posture test_version_compatibility.py:263 store_posture 按既有 STORE_CLASSES 分类，把每个 durable/derived store 模块分区到「已迁移」或「未版本化」 精确 partition：给未版本化 store 补迁移时，必须把它从 UNVERSIONED_STORES 搬到 MIGRATION_STORES

未版本化的 store 不是「漏了」——设置面列变更走 ensure_column、向量索引派生重建、 观测日志没有兼容语义；但每一行都要求非空理由 test_version_compatibility.py:634 UNVERSIONED_STORES， 不允许用沉默表示「不需要」。迁移侧同理 test_version_compatibility.py:561 MIGRATION_STORES： 冻结的是实测最大版本，测试如实测值对不上就红。

一条纪律值得单独说：缺口也要引 golden test_version_compatibility.py:678 GAPS。 缺口行不是注释，而是一条被测试钉住的现状——「新版本被原样保留」这件事有 golden 证明。 将来真给这个缺口加门时，那条 golden 必红：改行为的人被迫在同一提交里改注册表与文档。 这是有意的摩擦——兼容语义变化本来就该是一次显式决定，而不是一次顺手的重构。

代码与注册表之间还有一道对账：冻结值测试把 AST 检测到的常量与字面量跟注册表逐行比较； 少数名称不含 VERSION 的 curated 常量经 importlib 取出活对象再比； 产品版本则与 pyproject.toml 核对。于是「代码改了、注册表没改」 和「注册表改了、代码没改」都会在 CI 里当场变红——不需要等到某次升级事故才发现。

现状缺口：一条，写在明面上

缺口现状风险本批为什么不补
evalset-newer-refusal parse_evalset models.py:328 parse_evalset 接受任意整数版本并原样保留；非整数才折回默认 新版本的资产会被旧代码继续读写，可能悄悄丢掉新字段的语义 拒绝新版本会影响现有资产文件的向前兼容体验，留给 evalset 自己的升级批次决定策略

反面例子同样重要：analysis payload 的「键在场容忍」不是缺口，是机制。 它的兼容判据是「键在不在」而不是版本号—— engine.py:1675 version 的 version 字段只写不读，老读端忽略新键、新读端对缺席整节不渲染。 把它误登记成「版本门缺失」会导致有人去加一个没有消费者的门——注册表的价值一半在于把「不是问题」也写清楚。

已补齐：OSSIE 根形状与版本门

原先的 ossie-version-gate 缺口已经关闭。语义文档现在按 OSSIE 0.2 扁平根读写：模型字段（name / datasets / metrics / relationships） 直接在文档根，masking / topics / hierarchies / time_spine 与它们同层。 非空文档必须带可解析的字符串 version；比本程序支持的版本 更新就拒绝（升级 Trove 或回退文件），更老的扁平版 收养并保留文件里的版本字符串。

旧 v0.1 的 semantic_model 列表包装被硬拒绝， 错误文案给出可执行的迁移命令；存量文件经纯转换器 ossie_migrate.py convert_text 升级（保留注释与键序，转换后做 YAML 数据等价与解析回环两道校验）。 写路径统一经 ossie.py stamp_ossie_version 盖章：version 放第一键、老扁平版升到当前、更新版本拒绝写。 镜像与语义层在读不懂文件时保留 last-known-good，并把原因写进拒绝报告—— 「文件是新的、代码是旧的」不会退化成一次静默的空模型。

怎么用：新增一个版本点

  1. 先确定类别与两扇门。写下 kind、读到更新版本的行为、读到更老版本的行为； 如果两扇门都不是 n/a，就必须能指出一个钉住该行为的测试——没有证据的兼容声明不算声明。
  2. 登记。常量进 CONSTANT_KEYS + REGISTRY；载荷字面量进 LITERAL_WRITE_KEYS；迁移进 MIGRATION_STORES（从未版本化 store 搬行，不是两处都写）。
  3. 同提交补证据。行为中性 golden 放在属主测试文件里，注册表只引用 pytest node id； 缺口行同样要引 golden——它钉的是「现状被看见」，不是「现状没问题」。
  4. 跑门。uv run pytest tests/architecture/test_version_compatibility.py -q 与 python3 scripts/check_page_anchors.py --at HEAD；前者守注册表，后者守这页的源码锚点。

改已有版本值时的顺序相反：先让冻结值测试红，再从失败消息里读到该改哪一行—— 「代码改了、注册表忘了」与「注册表改了、代码忘了」都会被同一道门拦下。

取舍

选择放弃了什么为什么值得
注册表放测试，不进运行时 生产环境对「未登记版本点」的即时拦截 零运行时门禁、零行为变化；新版本点的风险在合并前暴露，而不是上线后多一条不可控的失败路径
冻结字面量（非引用常量） 改版本时少改一处 要改两处正是设计目标：一次兼容语义变化应该被看见，而不是被一次重构带走
证据用 pytest node id 自由文本的说明弹性 可静态校验、会腐烂得响亮；证据是「有人真的钉过」，不是「有人说过」
缺口也钉 golden 补门时的一次顺手改动 兼容行为变化必须同时改注册表与文档——有意的摩擦比无声的漂移便宜
未版本化 store 只登记理由 给每个 store 都补一套迁移 K/V 设置面、派生索引、观测日志没有版本语义；为它们造版本只会制造维护面
页面不写具体版本值 文档自带的「速查数字」 注册表是唯一权威；文档写数字就是第二次漂移的起点，机制才是文档该讲的东西
棘轮而非沙箱 对动态 importlib / getattr 的覆盖 AST 覆盖明确可解释；诚实标明盲区，比假装全覆盖更可靠。新误报必须显式登记，不许静默放宽
